Implementation plan · Responses API · Codex CLI

Give the full Responses tool set of Codex through copilot-api

A plan in stages to support the non-function Responses tools that Codex CLI needs. These tools are freeform custom tools such as apply_patch, MCP tools in a namespace, and tool_search. The plan keeps the primary safety rule of the proxy: the proxy never runs a tool that the client owns.

Summary

The proxy accepts Codex-shaped Responses requests in permissive mode. But it sends only type: "function" tools to the GitHub Copilot SDK. This removes the tools that Codex models need for a complete coding-agent function. The removed tools are apply_patch as a freeform custom tool, MCP tools in Responses namespaces, and the tool_search discovery tool.

Implementation method: add a normalized Responses tool catalog. Change each supported client-owned tool into an SDK-compatible custom tool. Record each SDK tool call with sufficient metadata to build the original Responses output item again. Extend the parser of the continuation for the related output items.

This work does not need the built-in shell, file or MCP tools of the Copilot SDK. The SDK stays a transport for the model. Codex CLI stays the program that runs the tools.

Current state

The related implementation paths are narrow, and they are conservative on purpose:

  • internal/openai/types.go models a tool primarily as Type plus a nested Function.
  • internal/openai/validation.go lets non-function Responses tools pass in permissive mode, but it then ignores them.
  • openai.SupportedTools returns only the tools where tool.Type == "function".
  • internal/httpapi/responses.go sends only SupportedTools(req.Tools) to the gateway.
  • internal/toolproxy/toolproxy.go registers only those function tools as SDK custom tools.
  • README.md gives the current behavior: the proxy ignores non-function Responses tools from Codex CLI in permissive mode, and rejects them in strict mode.
Observed effect: a Codex CLI request can contain all the tools, but the model gets only the subset that passed SupportedTools. Thus the other tools are absent from the behavior of the model. They are not absent from the local tool runtime of Codex.

Architecture

The primary pattern is normalize → flatten → call → build again → continue.

1. Normalize

Parse the tools array of the incoming Responses request into a typed catalog. The catalog keeps the raw JSON, the public names, the namespace metadata, the output kind, and the validation state.

2. Flatten

Change each supported client-owned tool into a Copilot SDK custom tool. Give it a safe internal SDK name, and keep a map back to its Responses identity.

3. Call

Let the model call the SDK custom tools. The handler stops the turn and waits while Codex CLI runs the true tool.

4. Build again

Change each recorded SDK call back into the correct Responses output item type: function_call, custom_tool_call, or tool_search_call.

Implementation phases

Phase 0

Record the exact Codex request and the shape of the model discovery

Do not change the behavior first. Add local fixtures for reproduction, and add a log of the request shape. Then the implementation uses true Codex CLI payloads.

  • Add a debug log with redaction under COPILOT_LOG_CONTENT. The log counts the tool types and prints the names and the namespaces. By default it does not print the full schemas.
  • Add a fixture that uses the list which the user observed. The list has a usual function tool, function names with a dot such as multi_tool_use.parallel, the custom tool apply_patch, a namespace with child tools, and a top-level tool_search.
  • Put the exact wire shapes in the fixture. Use custom with name, description and format {type, syntax, definition}. Use namespace with name, description and child tools. Use tool_search with execution, description and JSON-schema parameters.
  • Find if the absent tools are present in the incoming /v1/responses requests. If they are not present, find if the Codex model metadata removed them earlier.
  • Record which model endpoint Codex CLI calls (/v1/models, /codex/models?client_version=..., or another configured path). Do this before you add a compatibility mode for the metadata.

Phase 1

Add a catalog of the Responses tools

Replace the helper path that supports functions only. Use a fuller representation for the Responses tools. Keep Chat Completions with functions only.

  • Add a new type such as openai.ResponsesTool. As an alternative, extend openai.Tool with raw fields for function, custom, namespace and tool_search.
  • Make NormalizeResponsesTools(req.Tools, strict). It returns the supported client-owned tools. It also returns clear diagnostics for the ignored tools and the unsupported tools.
  • Do not change ValidateTools for Chat. Update ValidateResponsesTools to check the supported Responses-only types in strict mode and in permissive mode.
  • Keep strict, defer_loading, format, execution, the metadata of the namespace children, and the raw JSON. Then the proxy can send tool_search_output.tools back with no loss.
  • Define the validation matrix for strict mode and permissive mode, and test it. Do this before you change the behavior at runtime.
Phase 2

Flatten the supported tools into SDK custom tools

Extend internal/toolproxy. Each normalized Responses tool becomes one SDK custom tool. A namespace becomes more than one SDK tool, one for each child.

  • Define a ClientTool metadata structure with SDKName, Kind, ResponseName, Namespace, Description, Parameters, Strict, DeferLoading, and the original raw specification.
  • Use deterministic SDK-safe aliases for each tool kind when the public Responses identity is not safe for the SDK. This includes function names with a dot such as multi_tool_use.parallel. It is not limited to the namespace children.
  • For a direct function with an SDK-safe name, keep the public name. Keep it only when it does not collide with another encoded alias or with a reserved name.
  • For custom, make an SDK JSON schema with a necessary string field input. Add a description that explains the freeform shape that comes after.
  • For namespace, flatten each child into a deterministic safe SDK name, for example mcp__grep_app__searchGitHub. Store the Responses namespace separately.
  • For tool_search, make an internal SDK alias for the canonical top-level tool_search tool. Use the given schema of the query and the limit. The alias must never go into a Responses output item.
  • Find and reject each collision between the direct safe names, the encoded aliases, the loadable tools that come back, and the reserved names such as __copilot_api_no_tools__. Do this before the session starts.
Important: the SDK transport gives custom tools with a JSON schema. It does not give the native freeform grammar tools of OpenAI. The adapter must keep the output shape of Codex. But the prompt or the schema that the model gets can need a small compatibility layer for freeform custom tools.
Phase 3

Add a general carrier for the recorded calls and the continuation outputs

The current pipeline carries only []openai.ChatToolCall and function outputs of the type map[string]string. The extended Responses tools need typed carriers for the calls and the outputs in httpapi, copilotgw and toolproxy.

  • Add an internal type for a recorded call, for example toolproxy.CapturedCall or copilotgw.ToolCall. Give it Kind, SDKName, ResponseName, Namespace, CallID, ArgumentsJSON, Input, Execution and the raw metadata.
  • Keep the adaptation of Chat Completions to []openai.ChatToolCall. Make the serialization of Responses use the general call type.
  • Add an internal type for a continuation output with Kind, CallID, Output, an optional Name, Status, Execution, and the Tools that come back.
  • Send these types through parseResponsesInput, copilotgw.ResponseRequest, the match of the pending batch, the completion of the batch, the construction of the fallback transcript, and the serialization of the response.
  • When the SDK calls a flattened namespace tool, store the namespace and the child name. Then the Responses item can be built again.
  • When the SDK calls a custom tool, take the raw input string out of {"input":"..."}. If the JSON is malformed, return a tool error that the model can see.
  • When the SDK calls tool_search, keep the arguments as structured JSON. Do not keep them as string-only function arguments.
Phase 4

Build the Responses output item types again

Update the gateway and the stream encoder. They must write the item type that Codex CLI needs. Each call kind must have a stable call_id value.

  • Add fields to openai.ResponseOutputItem, or add custom marshaling, for Namespace, Input, Execution, and the raw or structured arguments of tool_search_call.
  • Make sure that function_call.arguments stays a JSON string. Make sure that tool_search_call.arguments serializes as an object.
  • Write a direct function tool as {"type":"function_call","call_id":"call_...","name":"exec_command","arguments":"..."}.
  • Write a namespace child as {"type":"function_call","call_id":"call_...","namespace":"mcp__grep_app","name":"searchGitHub","arguments":"..."}.
  • Write a custom tool as {"type":"custom_tool_call","call_id":"call_...","name":"apply_patch","input":"..."}.
  • Write a discovery call as {"type":"tool_search_call","call_id":"call_...","execution":"client","arguments":{...}} with no name and no namespace.
  • Store the same output items in the stored Responses records. Then the fallback after a restart or a TTL gets the canonical Responses shapes, and not the SDK aliases.
Phase 5

Support the continuations for the new output kinds

Codex CLI answers a custom call and a discovery call with input item types that are different from the types of a usual function call.

  • Extend ResponseInputItem, or keep the raw JSON of each item, for namespace, status, execution, tools, and the optional name on custom_tool_call_output.
  • Extend parseResponsesInput. It must know custom_tool_call_output and tool_search_output, and also function_call_output.
  • Use outputRawToString again for custom_tool_call_output.output. Keep the support for text parts and for structured content. Accept the optional name when it is present, and check it.
  • For tool_search_output, the matching call_id is necessary. Check execution: "client" for a client-owned call. Parse status. Parse tools as loadable Codex specifications.
  • Limit tool_search_output.tools to loadable function and namespace specifications. Use the validation matrix to reject, or to ignore with a diagnostic, the hosted specifications, the custom specifications, the nested namespaces and the tool_search specifications that come back.
  • Check that the type of the continuation item agrees with the kind of the pending call. Do this for the active matched IDs only. This keeps the current behavior for the stateless history of Codex, where old outputs can come together with one live batch.
  • Update the reconstruction of the fallback transcript. It must include custom_tool_call_output, tool_search_call, tool_search_output, and the history of a function_call with a namespace, when no live pending batch is available.
Phase 6

Make tool_search a continuation that stops the turn

tool_search_output.tools cannot make the new tools callable in an SDK turn that is already configured. The implementation must show this limit clearly. It must not act as if the SDK tools can change during a turn.

  • A live pending tool_search_call gets a tool_search_output. Do not only release the parked SDK tool handler and wait for the new tools to appear.
  • Record the result of the search in the transcript and in the stored response. Add the loadable specifications that came back to the normalized catalog. Then start or continue a new SDK model turn with the merged catalog for the continuation of the model after the search.
  • The constraints of the SDK or of the session can prevent this new-turn method in the first implementation. Then limit the behavior clearly: accept and store tool_search_output. The tools that came back become available only when the client sends them again in tools on a new request.
  • Add tests that prove this rule: the tools that came back are not callable until the new tool catalog is installed in the configuration of the SDK session.
Phase 7

Keep the safety rules

Do not make this proxy into a runtime that runs the tools on its side.

  • Continue to make the Copilot client with ModeEmpty.
  • Keep AvailableTools limited to the synthetic custom tools of the request, or to the sentinel name that no tool can use.
  • Keep the approval of the permissions limited to the exact SDK names of the request.
  • Obey tool_choice: "none". Give no synthetic tool to the model, and this includes custom, namespace and tool_search.
  • Do not configure MCP servers on the proxy. Do not configure skills, a shell, repository operations, memory, file access, hosted web search or hosted image generation.
  • Add regression tests. They must prove that the built-in tools of the SDK stay unavailable when Codex CLI gives namespace MCP tools.
Phase 8

Update the Responses WebSocket path and the warm-session path

The target of this work is compatibility with the Responses API. Thus the WebSocket transport and the warm sessions with generate:false must support the same normalized catalog. If they do not support it, the document must say clearly that they are not in the scope.

  • Replace the storage and the comparison of openai.SupportedTools(req.Tools) in a warm session with the normalized catalog of the client tools.
  • Make sure that the WebSocket response.create accepts the same extended tool specifications. It must write the same output items, and it must process the continuations of the extended tools with the same validation rules as HTTP.
  • Add tests for the reuse of a warm session and for a catalog mismatch. Include the custom tools, the namespace tools, the function names with a dot, and the tool_search tool.
  • If the WebSocket work cannot be complete in this part, add a control for the feature and write it in the documentation. Add tests that prove that an unsupported extended-tool WebSocket request fails with a clear error, and does not remove tools quietly.
Phase 9

Add Codex model metadata only if the recorded requests show that it is necessary

The model metadata of Codex controls some Codex tools before the request. The important fields are apply_patch_tool_type and the support for the search tool. The first implementation must not guess. It must record if Codex sends the absent tool specifications, and which model endpoint shape it uses.

  • If Codex already sends custom, namespace and tool_search, do not change the model responses for this feature.
  • If Codex does not send apply_patch or tool_search because the metadata is absent, add a Codex metadata compatibility mode that the user must select. Do not change the shape of the OpenAI model list for all users.
  • Possible metadata fields: apply_patch_tool_type: "freeform", supports_search_tool: true, supports_parallel_tool_calls: true, and related hints for the context and the truncation.
  • Add these fields under data[].metadata only if Codex reads the OpenAI model-list envelope. If it does not, make the exact model endpoint shape that Codex CLI requests.
  • Document and test each new configuration option such as COPILOT_CODEX_MODELS_COMPAT=1. Prove that the default output of /v1/models does not change.

Proposed data model

type ResponsesToolKind string

const (
    ToolKindFunction   ResponsesToolKind = "function"
    ToolKindCustom     ResponsesToolKind = "custom"
    ToolKindNamespace  ResponsesToolKind = "namespace"
    ToolKindToolSearch ResponsesToolKind = "tool_search"
)

type NormalizedTool struct {
    Kind         ResponsesToolKind
    Name         string          // public function/custom/tool_search name or namespace name
    Namespace    string          // set for namespace children
    Description  string
    Parameters   json.RawMessage // JSON schema when applicable
    Format       json.RawMessage // custom/freeform grammar metadata
    Execution    string          // tool_search execution, usually "client"
    Strict       *bool
    DeferLoading *bool
    Children     []NormalizedTool // namespace children
    Raw          json.RawMessage
}

type ClientTool struct {
    SDKName      string          // safe SDK-facing alias
    ResponseKind ResponsesToolKind
    ResponseName string          // canonical Responses-facing name
    Namespace    string
    Description  string
    Parameters   map[string]any
    Strict       *bool
    DeferLoading *bool
    Raw          json.RawMessage
}

type CapturedToolCall struct {
    Kind          ResponsesToolKind
    SDKName       string
    ResponseName  string
    Namespace     string
    CallID        string
    ArgumentsJSON json.RawMessage // function/namespace/tool_search args
    Input         string          // custom/freeform raw input
    Execution     string          // tool_search execution
}

type ResponseToolOutput struct {
    Kind      ResponsesToolKind
    CallID    string
    Name      string          // optional custom_tool_call_output name
    Output    string
    Status    string          // tool_search_output status
    Execution string          // tool_search_output execution
    Tools     json.RawMessage // tool_search_output loadable specs
}

The exact names can change during the implementation. The important property is different: the SDK name is an internal detail, and the Responses identity stays complete for the client. Chat Completions can continue to adapt the recorded calls to []openai.ChatToolCall. Responses must use the general types for the recorded call and the output.

Streaming and continuations

The stream of a function call writes response.output_item.added, the deltas of the arguments, the end of the arguments, and the end of the output item. For a new call type, the minimum compatible stream must also announce each item before it completes it. Write response.output_item.added, then response.output_item.done, then response.completed. Deltas with more detail are optional in the first implementation.

Call kind Output item of a non-stream response Minimum for the stream Continuation input
Function function_call with call_id The current lifecycle of a function call function_call_output
Namespace child function_call with call_id and namespace response.output_item.added + response.output_item.done function_call_output
Custom or freeform custom_tool_call with call_id response.output_item.added + response.output_item.done custom_tool_call_output
Tool search tool_search_call with call_id and execution response.output_item.added + response.output_item.done tool_search_output
Later improvement: add delta events with more detail after the basic compatibility operates, if Codex or another client needs them. Use the exact name of the Codex custom input event, response.custom_tool_call_input.delta, for the stream of a custom freeform tool. Do not use response.function_call_arguments.* for it.

Codex model metadata considerations

The OpenAI-compatible /v1/models endpoint of the proxy has the shape of the OpenAI model list on purpose. But Codex has model metadata fields that change how it plans the tools. This feature must not change the contract of the model list for all users without evidence.

  1. Measure first: record a true Codex run. Find if the absent tools are present in tools. Find also which model endpoint shape Codex requested.
  2. If the tools are present: the change to the tool filter is sufficient. Do not change the model metadata.
  3. If the tools are absent: add a compatibility mode that the user must select, for example COPILOT_CODEX_MODELS_COMPAT=1. It adds fields only to the model response shape that Codex reads.
  4. Do not claim too much: declare only the capabilities that the proxy can send in both directions safely. For example, declare apply_patch_tool_type only after the support for custom_tool_call is complete. Declare the support for the search tool only after the tool_search_output lifecycle is complete, or after you limit its scope clearly.
  5. Document the option: if you add a compatibility mode, update the configuration table in the README. Add tests that prove that the default model output does not change.

Strict/permissive validation matrix

The implementation must make the validation behavior clear before the changes to the runtime start. The proxy accepts the supported client-owned Responses tool types in both modes. In permissive mode, the proxy removes the unsupported tools that the host or the proxy must run. It does not give them to the model, and it does not run them. In strict mode, the proxy rejects them.

Test plan

Unit tests

  • Unmarshal the function, custom, namespace and top-level tool_search specifications, and check them.
  • Update the current tests that check the old behavior with functions only. Examples are the tests of the permissive Codex defaults, and the sentinel tests with unsupported tools only.
  • Reject a malformed namespace, a duplicate flat SDK name, a nested namespace, a dangerous loadable specification that came back, and an unsupported hosted tool. Use the validation matrix.
  • Check the SDK-safe alias for an unsafe function name such as multi_tool_use.parallel, for a custom tool, for a namespace child, and for tool_search.
  • Check the schema that the proxy makes for the custom tool apply_patch. Check also that the proxy takes the input out correctly.
  • Check that strict, defer_loading, the raw format, and the raw loadable specifications that came back stay unchanged.

Tests of the HTTP layer and the gateway

  • A Responses request with mixed tool kinds sends all the supported normalized tools to the gateway.
  • A non-stream response serializes custom_tool_call, a function_call with a namespace, and tool_search_call, each with a stable call_id value.
  • The SSE stream writes output_item.added before output_item.done for each new call kind. The output indexes stay stable when a reasoning item or a message item comes before the tools.
  • The continuations accept custom_tool_call_output and tool_search_output. This includes the optional custom output name, and the status, execution and tools fields of the tool search.
  • These conditions fail with a clear error: an incorrect output kind for the kind of the pending call, an absent call_id, a duplicate live call_id, a model mismatch, and a mismatch of the previous response.
  • The cold fallback path, the restart path and the TTL path build the transcripts again for the custom calls, the calls with a namespace, the tool-search calls, and their outputs.

Tests of the safety and the transport

  • A request with no tools gives the sentinel name that no tool can use.
  • tool_choice: "none" with function, custom, namespace and tool_search tools keeps back all the synthetic SDK tools.
  • MCP namespace tools in a request do not configure MCP servers on the proxy.
  • The permission handler approves only the exact synthetic SDK names.
  • The built-in tools of the SDK stay disabled with ModeEmpty.
  • The Responses WebSocket response.create and the warm sessions with generate:false store, compare and use again the normalized extended tool catalogs. As an alternative, they fail with a clear error, and the documentation gives the limit of the scope.

End-to-end tests and deterministic integration tests

  • Use a record of a false SDK or provider. Check the exact names, descriptions and schemas of the SDK Tools and AvailableTools, and the filters of the request.
  • Run Codex CLI against the proxy as a first test, and ask it for the list of the tools. Remember that the model output is not deterministic.
  • Check that this list includes apply_patch, a minimum of one child tool of an mcp__* namespace, and the top-level tool_search.
  • Do a small apply-patch cycle in a workspace that you can delete after the test.
  • Do one cycle with a namespace child of MCP. Use a false local MCP server that the test controls.
  • Do a tool_search cycle. Prove that the tools that came back become callable only after the clear new-catalog limit of the implementation.

Rollout and risks

Risk Impact Mitigation
The encoding of the SDK name changes the behavior of the model The model can list or call an encoded name in place of the canonical name of Codex. Keep each name as near to the original as safety permits. Put the canonical namespace and name in the description. Build the output names again independent of the SDK name.
The SDK gets a freeform tool as a JSON schema The model can put apply_patch in an incorrect wrapper. Use one input field with a strong description. Add tests of the prompt and the schema. Add a fallback parser for the usual shapes.
The tool search needs a tool set that changes during the turn A loaded tool can be not callable in the same SDK turn. Make the clear limit of a new turn with a new catalog. As an alternative, make the scope smaller until the function is available. Never say that a tool that came back is callable before the SDK configuration proves it.
The proxy runs a tool by accident This breaks the security expectations and the scope of the project. The handlers continue to wait and to return the outputs of the client only. Add clear regression tests for the safety.
A regression in the compatibility with OpenAI A client that is not Codex can get a different behavior. Keep Chat Completions with functions only. Document the extended-tool behavior of Responses, the validation matrix, and the difference between removal and rejection of a hosted tool.
The WebSocket path and the warm-session path become different from the HTTP path HTTP operates correctly, but the Codex WebSocket or generate:false removes tools quietly or disconnects the warm sessions. Update the comparison of the warm-session catalog, and add tests for the WebSocket. As an alternative, refuse the transport paths that are not supported.

The recommended rollout makes the supported client-owned Responses tools available by default after the tests pass. Strict mode must accept the client-owned types that become supported. It must still reject a malformed tool, a hosted tool, a tool that the proxy must run, and an unknown unsafe tool. The updates of the README are part of the rollout. They include the validation matrix, the limit of the tool search, the scope of the WebSocket work, and each option for the compatibility of the Codex model metadata.

Acceptance criteria

  1. A mixed Codex Responses request contains function, custom, namespace and top-level tool_search tools. The proxy no longer removes the last three types.
  2. The proxy gives a safe SDK alias to an unsafe Responses function name such as multi_tool_use.parallel. It then returns the original public name.
  3. Codex CLI can see and name the tools that were absent, when a user asks it for the list of the available tools through this proxy. The tools are apply_patch, a minimum of one child tool of an mcp__* namespace, and tool_search.
  4. Each call item that the proxy writes has a stable unique call_id. The value agrees with the pending batches, the stored responses, the streamed items, and the continuation input items.
  5. apply_patch makes a custom_tool_call with the raw input. It accepts a custom_tool_call_output continuation.
  6. A child tool of an MCP namespace makes a function_call with a namespace. It accepts a usual function_call_output.
  7. tool_search makes a tool_search_call and accepts tool_search_output. It then installs the loadable tools that came back at a clear new-catalog limit. As an alternative, it clearly limits those tools to a later new request.
  8. tool_search_output.tools accepts only loadable function and namespace specifications. It applies the same validation of the aliases, the collisions and the safety as the tools of the first request.
  9. The stream writes response.output_item.added before response.output_item.done for each new call kind. The sequence numbers and the output indexes stay stable.
  10. The Responses WebSocket path and the warm-session path support the normalized extended tools with tests. As an alternative, they fail or refuse the unsupported extended-tool requests with clear errors.
  11. tool_choice: "none" with extended tools gives no synthetic SDK tool to the model.
  12. No shell, file, MCP, memory, skill, repository, hosted web-search or hosted image-generation tool of the proxy becomes available. Such a tool becomes available only if the client sent it in the request as a client-owned tool specification.
  13. The strict behavior and the permissive behavior agree with the validation matrix. The README gives both.
  14. If the compatibility with the Codex model metadata is implemented, the user must select it. It is documented and tested. It does not change the default output of /v1/models.
  15. The current behavior of the function tools of Chat Completions does not change.
