Implementation plan · Responses API

WebSocket mode for Responses workflows that run for a long time

A plan in phases. It adds an OpenAI-compatible WebSocket transport to /v1/responses. It uses again the Responses validation, the streaming event model, the Copilot SDK gateway, the code for the continuation of a tool call, and the guarantees for the isolation of the prompt.

Summary

The WebSocket mode of the OpenAI Responses API keeps a connection to /v1/responses open. The client sends response.create events on the socket. The server returns the same Responses streaming events that SSE uses now. The largest difference in behavior is the continuation. The open socket keeps the most recent response state in memory. Thus a store:false chain continues, and the server does not write API-visible response state to the disk.

The recommended strategy: add a WebSocket transport layer in internal/httpapi. The layer changes each socket message into the copilotgw.ResponseRequest path that exists now. Move the serialization of the stream events out of the SSE handler, so that the two transports use it. The gateway stays the only component that controls the behavior of the generation.

Use again

The validation, the parsing of the input, the selection of the reasoning effort, the registration of the tools, the session runners, and the schemas of the OpenAI response events.

Add

The control of the WebSocket upgrade, the parsing of the client events, the sequence of the turns on one connection, the response cache of one socket, and the writer of the JSON events.

Delay

Delay the separate /v1/responses/compact endpoint, if it does not get its own priority. Write in the compatibility matrix that the server does not support it.

The protocol contract

The first target for compatibility is the WebSocket mode in the document OpenAI API: WebSocket Mode. The project must support the documented main loop first. Add the other functions after that.

Client → server

{
  "type": "response.create",
  "model": "gpt-5.5",
  "store": false,
  "previous_response_id": "resp_123",
  "input": [
    {
      "type": "function_call_output",
      "call_id": "call_123",
      "output": "tool result"
    }
  ],
  "tools": []
}

Requirement The planned behavior
Endpoint Accept a WebSocket upgrade on GET /v1/responses. Refuse a GET that is not an upgrade. Return an error in the OpenAI format or 426 Upgrade Required.
Authentication Use the bearer-token middleware that exists now before the upgrade. Do not add a second path for the authentication.
Event type Support response.create. Return invalid_request_error for a client event type that the server does not know.
Fields that the server does not support Ignore or refuse a field with the same strict or permissive rules that HTTP uses. In WebSocket mode, stream and background do nothing, because the transport controls this behavior.
Order Run one response at a time on one connection. A queue is optional. The first version refuses a second response.create while a response is active, and gives a clear error.
The limit of the connection Close the connection or refuse new work after 60 minutes with websocket_connection_limit_reached. Make the limit configurable only if the tests need a shorter time.
Warmup Support generate:false in a second phase. The first version can return a documented error that tells that the server does not support it. Give the support when a safe path for the warmup of an SDK session is proved.

Architecture

WebSocket mode is a transport adapter. The HTTP handler controls the upgrade, the input and output of the events, the life of the connection, and the state that is local to the socket. The gateway controls the validation of the model, the Copilot SDK sessions, the construction of the response, the batches of tool calls, and the storage. 

flowchart TD
    Client[WebSocket client] -- response.create --> WS[httpapi responses WebSocket handler]
    WS --> Decode[Decode and validate client event]
    Decode --> Parse[Reuse Responses input parsing and reasoning resolution]
    Parse --> CacheCheck{previous_response_id in socket cache?}
    CacheCheck -- yes --> Fast[Use connection-local continuation metadata]
    CacheCheck -- no --> Store[Fallback to persisted response state when store=true]
    Fast --> GW[copilotgw.StreamResponse]
    Store --> GW
    GW --> Events[ResponseStreamEvent channel]
    Events --> Shape[Transport-neutral Responses event shaper]
    Shape -- JSON frames --> WS
    WS --> Client

The proposed map of the files

  • internal/httpapi/server.go — send GET /v1/responses to a handler for the WebSocket upgrade. Put the route before the route of the subtree of the response ID.
  • internal/httpapi/responses_ws.go — the WebSocket upgrade, the read loop, the guard for the sequential execution, the deadline of the connection, and the mapping of the close and the errors.
  • internal/httpapi/responses_stream.go — the conversion from copilotgw.ResponseStreamEvent to openai.ResponseStreamEvent values. The conversion does not know the transport.
  • internal/openai/websocket.go — the structs of the envelope of a client event, the helpers for the envelope of a WebSocket error, and optional constants for the close codes.
  • internal/copilotgw/responses.go — small extension points for the continuation records that are local to the socket. Add them only if a change in the transport alone is not sufficient.
  • internal/sessionstore/store.go — the first version does not need a change of the schema. Add helpers only if the fallback to the stored state needs a clearer meaning.
  • internal/httpapi/server_test.go or responses_ws_test.go — the tests for the protocol, the order of the events, the continuation, and the errors.
The decision about the dependency: use github.com/coder/websocket, if there is no strong reason to prevent a new dependency. The package is small. The maintainers keep it current. It knows the context, and it does not have the maintenance history of the older Gorilla package. Add it with go get. Then run goimports -w after your changes.

The state model

The main value of the OpenAI WebSocket mode is the continuation that is local to the connection. The implementation keeps a small record in memory for the latest response on each socket. It uses the stored state only as a fallback, and only when the rules let it.

Case The expected behavior The detail of the implementation
No previous_response_id Start a new chain of responses. Make a new resp_ ID and a new SDK session. Do this in the same way as the HTTP streaming.
The previous ID is the same as the socket cache Continue quickly. This includes a continuation with store:false. Use the metadata that is local to the connection to start the SDK session again. If that operation fails, build a synthetic prompt for the continuation.
The previous ID is not in the cache, and store:true Use the stored metadata of the response as a fallback, if the metadata is available. Use the LoadResponseForContinuation and Stored checks that exist now for the usual stored chains.
The previous ID is not in the cache, and store:false Return previous_response_not_found. Do not use the disk files that the server keeps for debug. The behavior must agree with ZDR.
The continuation fails with a 4xx or a 5xx error Remove the previous response from the cache. Delete the entry in the socket cache before you send the final error event.
A conflict in the design: the gateway stores response records for debug now, also when store:false is set. WebSocket mode must not use that debug storage as a source for the continuation of a store:false response that is not in the cache. Keep three separate concepts: the API-visible storage, the debug storage, and the cache that is local to the socket.

The phases of the implementation

Make one shared component that shapes the stream events

Move the code in streamResponses that changes the internal gateway events into OpenAI Responses stream events. The new helper does not know if the events go out as SSE lines or as WebSocket JSON frames.

  • Make an interface for the transport, for example responseEventSink, with Write(event openai.ResponseStreamEvent) error and Done() error.
  • Move these parts into the helper: the record of the message items, the done events of the output text, the events for the arguments of a function call, and the failure events.
  • Keep the SSE output equal, byte for byte, if this is possible. Change the related tests if the order of the events becomes more normalized.

Add the WebSocket upgrade and the basic event loop

Add the support of GET /v1/responses for a WebSocket upgrade. Read JSON messages from the client until the close, the deadline, or an error of the protocol.

  • Add the WebSocket dependency with go get github.com/coder/websocket.
  • Write responsesWebSocket(w, r) in internal/httpapi/responses_ws.go.
  • Use the middleware that exists now for the authentication, the logs, the recovery from a panic, and the request ID.
  • Give a maximum size to a message. Use COPILOT_MAX_REQUEST_BODY_BYTES, or a smaller limit for WebSocket if you add one.
  • Refuse an event type that the server does not know. Send a JSON error event on the WebSocket, and not a raw HTTP error after the upgrade.

Change response.create into the request format that exists now

Decode the WebSocket event into the openai.ResponsesRequest format. Then use again the validation, the parsing of the input, the filter of the tools, and the selection of the reasoning effort.

  • Add an envelope type with type, generate, and the embedded fields that create a Responses request.
  • Give stream the value true always. In permissive mode, ignore the value that the client sends.
  • Keep the strict compatibility behavior that exists now for the semantic fields that the server does not support.
  • Write a log when a generation starts. Add a tag for the transport, for example responses.websocket.

Let only one response run on one connection

The documented mode of OpenAI runs the responses in sequence on one socket, and it does not multiplex them. The implementation makes this rule clear.

  • An option for the first version: run the read loop in sequence. Do not read the next response.create before the current turn is complete.
  • If you add asynchronous reads later, use a mutex or a state machine, and refuse work that overlaps.
  • Cancel the active Copilot turn when the socket closes, or when the connection reaches the limit of 60 minutes.

Make the continuation cache that is local to the socket

Store the latest response record for the connection after a complete response, or after a response with a tool call. Use the cache before the fallback to the stored state when the client gives previous_response_id.

  • Put in the cache only the data that the gateway needs: the response ID, the SDK session ID, the model, the instructions, the input text, the output text and items, the previous response ID, the ID of the batch that waits, the path of the stored file, and the stored flag.
  • Keep only the most recent response in the first version, to agree with the documented behavior. Add a small LRU cache only if a true client needs it.
  • For store:false, let the continuation start only when the previous ID agrees with the cache of the connection.
  • If the continuation fails, remove the related state from the cache before you send the error event.

Support the continuation loops that have many tool calls

Make sure that a function_call_output continuation on the socket starts the SDK handlers that wait. The next response events go out on the same socket.

  • Use again the checks of the ownership of a batch that waits: the kind of the endpoint, the model, the previous response ID, and one output for each call that waits.
  • Make the error messages equal to the documented previous_response_not_found error and to the OpenAI envelopes for an invalid request.
  • Check more than one tool call in one batch, and more than one batch in sequence in one socket session.

Add the limits of the life cycle and the observability

Add the controls for production before you make the function available to all users.

  • Give a connection a maximum age of 60 minutes. Send websocket_connection_limit_reached before the close, if this is possible.
  • Write structured logs for these events: the socket opens, the socket closes, a response starts, a response completes, a response fails, the cache gives a hit, the cache gives a miss, and the connection limit closes the socket.
  • Keep the rules that hide the content. Include a body only when COPILOT_LOG_CONTENT=true.
  • Think about counters for the active WebSocket connections and for the refused requests that overlap. Add them if you need more than the logs.

Write the documentation of the compatibility and of the delayed work

Update the public documentation after the tests pass.

  • Add WebSocket mode to the sections of the README about the endpoints and the compatibility.
  • Write which functions the server does not support, or which functions come later: the generate:false warmup, if it is not available, the separate compaction, and each limit that is different from the limit of OpenAI.
  • Add examples with a small WebSocket client and with a continuation loop that has a tool call.

The test plan

The class of the test What the test covers
Unit test: the shape of the events Give the test the gateway deltas, the function calls, the completed responses, and the errors. Then check that the OpenAI Responses events are the same for the SSE sink and for the WebSocket sink.
Handler test: the upgrade An authenticated WebSocket upgrade is successful. An upgrade without authentication fails in the middleware that exists now. A GET that is not an upgrade gets a clean refusal.
Handler test: response.create A correct request sends response.created, the deltas, and the final response event. It does not send the SSE [DONE] marker.
Continuation test: store:false A previous ID on the same socket continues correctly. A new socket with the same ID gets previous_response_not_found.
Continuation test: store:true A new socket uses the stored response state as a fallback, when the server stored the previous response.
The loop of the tool calls The model sends a function call. The client answers with function_call_output. The runner that waits continues. The completed response goes out on the same socket.
The errors of the protocol Incorrect JSON, an unknown event type, an absent model, an unknown model, fields that the server does not support, and two creates that overlap. Each one returns a socket error event in the OpenAI format.
The life cycle The close of the socket cancels the active generation. The deadline sends websocket_connection_limit_reached. A continuation that fails removes the state from the cache.
The live test with a condition Use the conditions of the live-test environment that exist now. Run one short true Copilot WebSocket response. Also run a continuation with a tool call, if live tools are available.
The commands for the checks: run goimports -w on each Go file that you change. Then run go test ./.... Add a small test package for WebSocket before you change the live tests. Then you find each fault of the protocol without Copilot credentials.

The risks and the actions against them

Risk The action against the risk
A small difference between the order of the SSE events and the order of the WebSocket events Put the code that shapes the events in one place. Test the two transports with the same synthetic stream of gateway events.
A store:false response uses the disk state of the debug storage by accident For an uncached store:false response, need a hit in the socket cache. Test the success on the same socket and the failure on a new socket.
The SDK session does not start again in the quick way that the plan wants Use the behavior that exists now first. Use a synthetic continuation prompt only where the HTTP behavior uses one now.
A socket that stays open for a long time hides an SDK turn that does not continue Send the cancellation of the context when the socket closes. Apply the configured request timeout to each turn. Apply the socket limit of 60 minutes.
The batches of tool calls stay in the memory if a client disconnects during a turn Cancel the active runner. Remove the batches that wait and that the connection owns, when the socket closes or when a final failure occurs.
A new dependency gives more possibilities for an attack Select a small WebSocket library. Set its version in go.mod. Give a maximum size to a message. Test the JSON input with fuzz tests and with error tests.

The acceptance criteria

Must pass

  • wss://host/v1/responses accepts authenticated WebSocket connections.
  • A client response.create event makes Responses streaming JSON events in the OpenAI format.
  • Only one response runs at a time on one connection.
  • A store:false continuation on the same socket operates with previous_response_id.
  • A store:false continuation that is not in the cache returns previous_response_not_found.
  • A loop of tool-call continuations operates on one socket that stays open.
  • go test ./... passes.

Can come later

  • The generate:false warmup, if there is no safe SDK path for a warmup.
  • The separate /v1/responses/compact endpoint.
  • The multiplex function. OpenAI does not support it for this mode today.
  • A cache of the connection that holds more than one previous response.
  • Metrics in addition to the structured logs.
The definition of done: the compatibility matrix in the README gives WebSocket mode. Deterministic tests cover it. It runs a loop of agentic tool calls, and the client does not open a new HTTP or SSE request for each turn.
