Implementation Plan · copilot-api

OpenAI-compatible API gateway for GitHub Copilot models.

A plan in phases to build a Go service. The service gives endpoints that agree with the OpenAI Chat Completions API and the OpenAI Responses API. The GitHub Copilot SDK supplies the models. The service operates as a basic inference provider: no Copilot persona, no Copilot SDK tools by default, tool calls that the client owns, support for streams, and model discovery. More compatibility comes in later steps.

01Goals and boundaries

The project lets one user connect many OpenAI-compatible clients to a local proxy base URL at the same time. The user gets the models of the GitHub Copilot subscription. The first release must give a reliable compatibility core. It must not claim every OpenAI feature immediately.

Main goals

  • Give the endpoints GET /v1/models, POST /v1/chat/completions and POST /v1/responses.
  • Support buffered JSON responses. Support also server-sent event streams in the OpenAI format.
  • Change the model metadata, the assistant text events, the stream deltas, the usage events and the errors of the Copilot SDK into responses in the OpenAI format.
  • Do not use the default system prompt of the Copilot SDK. Do not use the coding-agent persona or the behavior instructions of the SDK. The model instructions must contain only the OpenAI system/developer/instructions content that the caller sends. They can also contain the minimum neutral text that the translation of the protocol needs.
  • Disable all Copilot SDK tools by default. The runtime must not read files or write files. It must not run shell commands, call MCP servers or use the memory. It must not call a tool of the SDK. A later opt-in feature can let one documented function operate.
  • Support the OpenAI tools that the client defines. Send their schemas to temporary custom tools of the SDK. Return each tool call to the client, and the client runs the tool. The API broker does not run the logic of the client.
  • Operate with the usual OpenAI SDKs. The user changes base_url, and also the API key when the authentication of the proxy is on.

Items that the first milestone does not include

  • Full agreement with every OpenAI request field. This includes the beta endpoint, the fine-tuning endpoint, the batch endpoint, the audio endpoint and the embeddings endpoint.
  • A method to go around the rules, the quotas, the model policies or the authentication of the Copilot subscription.
  • The use of Copilot as a coding agent, the Copilot CLI persona, or the Copilot SDK tools in the default behavior of the API.
  • The operation of any OpenAI tool call on the server. The server only moves the tool requests and the tool results. The client runs the tool.
  • A method to hide the differences in the model behavior that the agent rules and the session rules of the Copilot SDK cause.
Rule for the compatibility: the Copilot SDK is a transport for the model. It is not the persona of the product. First, build a small OpenAI-compatible API with good tests. Replace the default prompt of the SDK. Keep the SDK tools unavailable by default. Accept an unsupported option only when the service can ignore it safely. Return an invalid_request_error response in the OpenAI format when the client does not expect the service to ignore the option.

02The design decisions

A design review and two spikes made the implementation plan better. The two spikes are spikes/synthetic-session-hydration.md and spikes/tool-choice-enforcement.md. These decisions are part of the contract of the product. A later implementation spike can replace a decision.

The runtime and the state

  • The service is a proxy for one user with parallel clients. Many clients and sessions can be active. But there is only one Copilot account and one authentication context.
  • There is no global conversation. To continue a conversation, the client must send protocol state. Examples are previous_response_id and the pending tool-call IDs that the proxy gives.
  • The Chat Completions API keeps no state and uses the transcript. A usual Chat request fills a synthetic Copilot session with the history. This is the default method for the history.
  • The Responses API keeps state and is more accurate. It uses the stored SDK session again through previous_response_id.
  • The service keeps the session state for monitoring and debugging. It does not use the state again automatically.

The prompt and the SDK behavior

  • Always send SystemMessageConfig{Mode: "replace"}. Do not send nil. Do not use the append mode or the customize mode.
  • The service combines the first Chat system/developer messages and the Responses instructions into the replacement prompt. The service rejects a system message or a developer message in the middle of a conversation.
  • If the caller sends no instructions, use a replacement prompt with one space. If that fails, use this exact minimal prompt: You are a chat completion model.. Do not store an empty system.message event, because the SDK rejects it when it resumes the session.
  • Use the Copilot CLI that the SDK includes and that agrees with the SDK version. COPILOT_CLI_PATH is an advanced override.
  • Do not upgrade the SDK or the CLI before the tests pass. The tests are the hydration tests, the tool tests, the prompt-isolation tests and the provider-format tests.

Tools

  • These functions are off by default: the built-in tools of the Copilot SDK, MCP on the proxy, the config discovery, the skills, the memory, the shell tools, the file tools and the repository tools.
  • A client can define OpenAI function tools. The proxy registers the public names of the client tools with custom-tool filters for that request. The proxy returns each tool call to the client. The proxy does not run the logic of the client.
  • The service supports MCP on the client when the client gives the MCP tools as OpenAI function tools. MCP on the proxy is not part of the MVP.
  • The MVP supports tool_choice when it is absent, auto or none. The service rejects a forced function and required, because the SDK and the CLI do not apply them.
  • A tool output is a string first. The service also accepts a JSON object output or a JSON array output and changes it to JSON text. The MVP rejects a binary output and a multimodal output.

The operations and the storage

  • Each generation request needs model. If the model is unknown, the service refreshes the model cache one time and then rejects the request.
  • The authentication of the proxy is optional for the loopback address. If COPILOT_API_KEY has a value, the service needs bearer authentication. If it has no value, the service starts without authentication and writes a warning to the log. The default bind address stays the loopback address. A different bind address needs COPILOT_API_KEY.
  • The proxy sets no limit on the parallel requests and no generation timeout by default. The HTTP connection timeouts and the default limit of 100 MiB on the request body control the use of the resources. The TTL of a pending tool call stays configurable. It protects against a handler that waits too long.
  • Use the XDG directories for the data, the state, the cache and the config. Keep the session state without a change and for an unlimited time by default.
  • Include copilot-api purge [--dry-run] [--yes] in the MVP. The purge command stops while a server lock is active. The same lock prevents two servers that use one store.
Principle of the thin proxy: send the request to the SDK and to the service without a change, if the OpenAI compatibility and the safety do not need a different behavior. Do not add rate limits, schedulers or policy layers for this project.

03The proposed architecture

Keep the Copilot SDK behind small internal interfaces. Separate the parts that have a high risk. These parts are the synthetic session hydration, the proxy for the client tools, and the storage of the SDK sessions. The HTTP layer keeps the OpenAI format. The gateway controls the life cycle of the SDK and the dependency on the SDK version.

The HTTP and API layer

  • The routes, the parsing of the request, the optional bearer authentication, the request IDs, and the OpenAI-compatible error objects for /v1/*.
  • The writing of the SSE response. In the MVP the service sends each tool-call object complete from a buffer.
  • Simple operational JSON for /healthz and /readyz.

The compatibility layer

  • The structs of the OpenAI Chat Completions API and of the Responses API, the checks, the IDs, the usage, and the conversion of the errors.
  • The combination of the instructions into a replacement system prompt.
  • The conversion of the tool schema, the batches of pending tool calls, and the strict check of the tool output.

The Copilot integration layer

  • The start of the included CLI, the ping, the readiness, the model cache, and the life cycle of the SDK client.
  • The synthetic Chat hydration through a SessionFSProvider of this project.
  • The second use of the SDK session for the Responses API, the tool handlers that wait, and the collection of the events.

05The plan for the proxy of the client tool calls

The tool calls agree with the basic OpenAI provider model. The client declares the tools. The model decides if it calls a tool. The API returns the call to the client. The client runs the tool and sends the result back. The server only adapts the schema and synchronizes the two sides.

The client runs the tool

The model gets only the tools that the OpenAI request contains. The proxy registers the public names of the client tools with the custom-tool filters of the SDK, and returns each call. The client does the actions. The client can use MCP for a function tool.

No built-in tools of the SDK

The file, shell, MCP, memory, skill and repository tools of the Copilot SDK stay unavailable. The other SDK tools stay unavailable too. If an unknown SDK tool runs, the service breaks a rule and stops the turn.

The continuations that wait

When the model calls a tool, the Chat API and the Responses API hold the live proxy handlers of the SDK. The handlers wait for the exact outputs of the client. COPILOT_TOOL_CALL_TTL gives the maximum time.

The conversion of the incoming schema

  1. Accept only the OpenAI function tools in the MVP. Reject the hosted tools, MCP on the proxy, the file search, the web search, the computer tools, the browser tools, and each tool type that is not a function.
  2. Check the name of the function, the description, the JSON Schema parameters, the optional strict field, and the format of the request. There is no limit on the number of the tools by default. The limit on the request body still applies.
  3. Register each client tool with its public OpenAI name. Set the override flag for the built-in tools of the SDK. Then a client tool with the same name replaces the built-in tool.
  4. Set AvailableTools to the custom-tool filters of the request. For tool_choice: "none", set a value that no tool can match. Refuse each permission request of the SDK and each unknown permission request.
  5. Support tool_choice when it is absent, auto or none. Reject a forced function and required, because the SDK and the CLI cannot apply them.

The contract of the proxy handler

// Created per request from OpenAI function tool schemas.
func proxyToolHandler(inv copilot.ToolInvocation) (copilot.ToolResult, error) {
    call := PendingToolCall{
        OpenAIToolCallID: mapSDKCallID(inv.ToolCallID),
        SDKToolCallID:    inv.ToolCallID,
        PublicName:       inv.ToolName,
        ArgumentsJSON:    preserveArgumentsJSON(inv.Arguments),
    }

    publishCompleteToolCall(call)       // yields OpenAI tool_calls/function_call output
    result := waitForClientToolOutput() // parked until all batch outputs arrive or TTL expires
    return toolResultForLLM(result), nil // string passthrough or JSON text
}

The behavior of the Chat Completions API

StepBehavior of the serverBehavior of the client
The request contains tools Fill the synthetic session with the earlier Chat history. Resume the session with the replacement prompt. Register the public proxy tools. Send the last user turn. Send the usual OpenAI tools field. Set tool_choice to absent, auto or none.
The model calls tools Record one or more proxy calls of the SDK. Return the complete OpenAI message.tool_calls field. Keep the text that comes before the tool call. Set finish_reason to tool_calls. Keep the SDK handlers on hold. Run the named tools locally with the arguments that the server returns.

Then release the handlers that wait, and let the same SDK turn continue. Add one role: "tool" message for each returned call. Call /v1/chat/completions again before the TTL ends.
The stream Stream the text deltas. Put the tool calls in a buffer. Send the complete tool-call objects near the end. Send the last chunk with finish_reason: "tool_calls". Then send data: [DONE]. Collect the text and the tool calls. Run the tools after the stream ends. Then send the outputs.

The behavior of the Responses API

  1. Create the stored SDK session for the chain of the responses, or resume it. Use the same session for previous_response_id.
  2. When the model calls a proxy tool, return one or more function_call output items. Each item has a constant call_id, the public name and the arguments.
  3. The client runs the tools. The client sends function_call_output items with previous_response_id. A continuation array must contain only function-output items. The service rejects an array that mixes a prompt and a function output.
  4. The server checks the kind of the endpoint, the model, the owner, an unknown ID, an absent ID, a double ID, and that each pending call has one output. Then it releases the SDK proxy handlers that agree.
  5. If the pending state expires, set the kept metadata to expired. Stop the live SDK session and disconnect it. Keep the files for debugging. Return an expired-call error in the OpenAI format for a later continuation.

The rules for the tool output and the errors

The format of the output

  • A string output goes to ToolResult.TextResultForLLM without a change.
  • The service accepts a JSON object output or a JSON array output and changes it to JSON text. It keeps the raw JSON bytes when this is possible.
  • The MVP rejects a binary output, an image output, an audio output, a file reference, a part of an output, and a stream output.

The errors and the batches

  • A failure of a client tool is usual tool output content. It is not a failure of the HTTP layer or of the proxy.
  • The service supports parallel batches internally. A batch needs all its pending outputs before the continuation.
  • An unknown SDK tool call, a request for a built-in tool, an expired pending call, and a failure of the tool conversion are errors of a rule or of the upstream service. The service writes them to the log with the request IDs.
  • The TTL of a pending call is configurable. It protects against a handler that waits too long. It is not a policy for the retention of the debug data.

The technical spike and the compatibility decisions

  • Use spikes/synthetic-session-hydration.md as proof. It shows that the model uses the synthetic events.jsonl history as context after the resume.
  • Use spikes/tool-choice-enforcement.md as proof. It shows that the current SDK and runtime do not give a true forced or required tool choice. The generated RPC format of the v1 beta contains a low-level RequiredTool availability check. But the public MessageOptions that this service uses gives no forced tool call that agrees with OpenAI.

07The flows of the requests and of the events

The flow of the Chat Completions API

  1. If COPILOT_API_KEY has a value, check the Authorization: Bearer ... header. If it has no value on the loopback address, run without authentication and write a warning to the log. A different bind address needs COPILOT_API_KEY.
  2. Check model, the order of the messages, the support of the features, the schemas of the client tools, tool_choice, parallel_tool_calls, and each continuation with a tool output.
  3. For a usual Chat turn, move the first system and developer messages into the replacement prompt. Change the earlier messages into versioned SDK events. Resume the synthetic session. Send only the last user message.
  4. For a known tool continuation, compare each returned tool_call_id, the kind of the endpoint, and the requested model with the pending state. Then release the live SDK proxy handlers, and do not send a new prompt.
  5. Keep the built-in tools of the SDK off. Use the custom proxy tools of the request. Use no config discovery, no MCP, and no skills. Use a permission handler that refuses each request, with an exception for the exact proxy tools.
  6. Return OpenAI JSON or SSE frames. If the model calls a proxy tool, return the complete tool_calls field, keep the text that comes before the tool call, and end with tool_calls.
  7. Keep the state of the synthetic session and metadata.json in the XDG data directory for an unlimited time for debugging. Do not use them again automatically for a later Chat request.

The flow of the continuity of the Responses API

  1. If previous_response_id is absent, create a new stored SDK session and a new response record.
  2. If it is present, load the stored map. Resume the same SDK session with the same safety settings.
  3. For a function_call_output item, reject an array that mixes a continuation and a prompt. Check the kind of the endpoint, the model, the owner, an unknown ID, an absent ID, a double ID, and that each pending call has one output. Then release the proxy handlers that agree.
  4. For usual new input, send only the new input to the SDK session that you resumed.
  5. Save the metadata of the response, the ID of the SDK session, the model, the status, the output items, the IDs of the pending calls, the usage, and the store state that the API shows. The service keeps the debug files for an unlimited time, also when store:false stops the later retrieval.

08The plan for the tests

The fast tests that run by default

  • Unit tests for the check of the OpenAI schema and for the error object.
  • Tests for the generator of the hydration. They cover the parent IDs, the timestamps, the delimiters of the turns, the assistant text, the tool calls, the tool results, and the JSON conversion of copilot.SessionEvent in the two directions.
  • Tests for the combination of the instructions. They cover the order of the first system and developer messages, the rejection in the middle of the conversation, and the selection of the empty, space or minimal prompt.
  • Tests for the conversion of the tools. They cover the public names, the custom filters, the override of a built-in tool, the values auto and none of tool_choice and the rejection, the rules of parallel_tool_calls for each endpoint, and the conversion of the output.
  • SSE tests for the text chunks, the complete tool calls from the buffer, the text before the tool call, the last finish reasons, [DONE], and the cancellation.
  • Tests of the store for the XDG paths, the behavior of the lock, metadata.json, the unlimited retention, the dry run of the purge, and the refusal of the purge while the lock is active.

The integration tests with a condition

  • The live Copilot tests need COPILOT_API_LIVE_TESTS=1. They are not part of the default go test ./....
  • A test that the model remembers a nonce from the synthetic text history. A test that the model remembers a synthetic tool result.
  • A proof of the empty, space and minimal replacement prompt. The test records the system content that goes to the provider.
  • A proof that the built-in tools are off. No file, shell, MCP, memory or SDK tool is visible, and no such tool can run by default.
  • A record of the provider request for the availability of the tools. The request has tools: [] for none. It has only the custom-filtered tools for auto. It contains no true forced or required tool choice.
  • Compatibility tests with the OpenAI Python SDK and the OpenAI JS SDK against the local server.

The condition for an upgrade of the SDK

Do not upgrade the SDK or the CLI before these tests pass with the new version: the hydration tests, the tests of the hydration of a tool result, the tests of the replacement prompt, the tests that the built-in tools are off, and the provider-format tests of the tool choice.

09The security and the operations

The default settings for the security

  • The authentication of the proxy is on when COPILOT_API_KEY has a value. Without a key, the server binds only to the loopback address. It starts without authentication and writes a clear warning to the log. A different bind address needs a key.
  • Always replace the system prompt of the Copilot SDK. Do not use the default prompt of the SDK, the append mode, the customize mode, or a nil prompt.
  • Refuse each Copilot permission request by default. Permit only the exact proxy tools of the request. The handlers of these tools do no other action.
  • Disable the SDK tools, MCP on the proxy, the config discovery, the skills, the repository instructions, the access to the shell and to the files, and the memory by default.
  • Use the GitHub and Copilot authentication of the user who logged in. GITHUB_TOKEN is an optional override for the full process. The MVP has no GitHub authentication for each request.
  • When the service gets a remote image, it rejects a loopback host, a private host, a link-local host, a multicast host, and each other host that is not public. It rejects also a redirect to such a host. This decreases the risk of SSRF.

The state and the life cycle

  • Use the XDG data, state, cache and config directories. An environment variable can override each directory. Create a sensitive directory with 0700 and a sensitive file with 0600 if the system permits it.
  • Keep the session state without a change and for an unlimited time by default for debugging. Write the metadata.json file of the proxy in the directory of each kept Chat session and Responses session.
  • Use a server lock. It prevents two processes that use one store, and it makes copilot-api purge safe.
  • Do not add an automatic cleanup. The manual purge command is the cleanup method, and the user controls it.
  • The TTL of a pending tool call stays configurable. It stops the live handlers that wait, and it keeps the debug files.

The operations of the thin proxy

  • The proxy sets no limit on the parallel requests and no generation timeout by default.
  • The control of the HTTP connection, of the header and of the body has practical limits. These are the timeouts for the read of the header, for the read and for the idle time, and the default limit of 100 MiB on the request body.
  • The start, the readiness check, and the model refresh can have practical timeouts, because the start must not wait forever.
  • Use the included CLI that agrees with the SDK version. Stop the start or the readiness check if the SDK and the CLI do not agree, or if the model list fails.
  • The logs contain no prompt, no response, no tool argument, no tool output, no image data, no authentication header, and no token by default. COPILOT_LOG_CONTENT starts the optional logging of the bodies. It records the request body and the response body with a size limit. Do not use it with a log system that other people can read.
  • Each HTTP response contains X-Request-ID. A request ID from the client is metadata only.

10The risks and the corrective actions

RiskEffectCorrective action
The synthetic hydration depends on the internal rules of the SDK events A change of the SDK or of the CLI can damage the accuracy of the Chat history, and the service gives no message. Set the exact version of the SDK and of the CLI. Separate internal/hydration. Check the events that the service makes. Keep the transcript fallback as an alternative method. Permit an upgrade only after the live hydration tests pass.
The default prompt or the default tools of Copilot go into a request The API stops to operate as a basic inference provider. Always use the replacement mode for the system prompt. Test the empty, space and minimal fallback. Disable the built-in tools in more than one layer. Stop the turn if an unknown SDK tool runs.
The service cannot give the full behavior of the OpenAI tool choice A client that uses a forced function or required tool use can get direct text, but it expects a tool call. Support only auto and none in the MVP. Reject a forced function and required with errors in the OpenAI format. Write the proof of the spike in the documentation.
The tool-call continuations that wait keep live resources An SDK handler that waits can wait forever if the client does not return the outputs. Use a configurable TTL for a pending call. Stop a live session that expires, and disconnect it. Keep the expired state for debugging. Reject a late continuation with a clear message.
The unlimited retention stores sensitive data The prompts, the responses and the tool outputs stay on the disk until the manual purge. Use the XDG user directories with strict permissions. Document the sensitive data and the purge command. Remove the sensitive data from the logs by default. Give no endpoint that reads a Chat session.
More than one server process damages the store Two writers at the same time can damage the kept session state or the pending records. Get a server lock in the XDG state directory. The purge command stops while the lock is active. A user can run more than one instance only with different directories and different ports.
An unsupported OpenAI field gives the user an incorrect idea A client can think that the service used a parameter, but the SDK ignored it. The strict mode rejects the request by default. Each fallback and each near result must be clear and visible.

11The definition of done

  • A user can run the binary with the Copilot authentication of the login or with GITHUB_TOKEN. The user can set COPILOT_API_KEY. The user can call the service from curl and from the official OpenAI Python SDK and JS SDK.
  • The service uses the included Copilot CLI that agrees with the SDK by default. The readiness check fails if the SDK and the CLI do not agree, or if the model list fails.
  • The service has these endpoints, and the documentation describes them: GET /v1/models, /v1/chat/completions with a stream and without a stream, POST /v1/responses, GET /v1/responses/{response_id}, and DELETE /v1/responses/{response_id}.
  • The Chat Completions API uses the synthetic session hydration by default. It rejects an order of the messages that it does not support. It rejects the request when the hydration fails. It keeps the session state and the metadata for an unlimited time for debugging.
  • A Responses continuation uses the stored SDK session again through previous_response_id. The store behavior that the API shows through store is separate from the retention for debugging.
  • The service never uses the default system prompt or the coding-agent persona of the Copilot SDK. The tests prove the empty, space and minimal replacement behavior.
  • The tools of the SDK and MCP on the proxy are off. The service sends the OpenAI function tools of the client through the proxy with their public names and with custom SDK filters. It returns each call to the client. It continues from the outputs of the client after the check. The gateway runs no tool.
  • The documentation describes the tool rules of the MVP: tool_choice with auto or none only, one rule for parallel_tool_calls for each endpoint, the tool calls from a buffer in a stream, the string-first tool outputs, and the strict check of the call ID.
  • The service returns error responses in the OpenAI format for /v1/* always. The health endpoint and the readiness endpoint use simple operational JSON.
  • The service has the XDG data, state and cache directories, the server lock, the logs with the secrets removed, the request IDs, the unlimited retention, and copilot-api purge [--dry-run] [--yes].
  • The default tests pass with go test ./.... The live Copilot integration tests need an environment variable, and they must pass before an upgrade of the SDK or of the CLI.
Recommended first pull request: the base of the server, the XDG store with the lock, the start and the readiness check of the included CLI, GET /v1/models, and the proof tests for the hydration and for the tool choice. This work makes the compatibility base before the full behavior of the generation.
