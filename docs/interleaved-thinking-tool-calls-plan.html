Implementation plan · Chat Completions + Responses

Interleaved thinking & interleaved tool calls

A plan in phases. It shows the streamed reasoning, it keeps the interleaved thinking through the tool calls, and it writes the usual reasoning / reasoning_content / reasoning_details fields on the OpenAI-compatible interfaces. A live probe of the event stream of the GitHub Copilot SDK gives the data for the plan.

Summary

The Copilot SDK already streams the model reasoning as incremental deltas. It also gives encrypted "opaque" thinking on every turn. But copilot-api puts all of this into one hidden TurnResult.Reasoning string. The code never writes, streams or replays that string. This plan sends the reasoning to the wire. It uses the fields that true clients already know (Open WebUI, Jan, OpenCode, Pi). It keeps the interleaved thinking through the usual tool loop that uses more than one request. It also removes the artificial refusal of parallel_tool_calls=true.

Recommended strategy: change the internal event model in internal/copilotgw/turn_runner.go first. That file is the one point where the code makes the SDK events flat. Then make the wire types of internal/openai and the two HTTP encoders larger. Chat Completions is the primary target. Responses gets the ordered-items mapping, which has more fidelity. The order of the SSE chunks keeps the order of the reasoning. OpenRouter, Ollama, vLLM and DeepSeek use the same method.

Reuse

The ordered event callback of the SDK, the batch model and the continuation model of toolproxy (they already accept more than one call), the session hardening, the resolution of the reasoning effort, and the SSE writers.

Add

The reasoning_delta stream events, the reasoning / reasoning_content / reasoning_details wire fields, the capture of the opaque thinking, and a control for the emission policy.

Defer

The portable stateless round-trip of the encrypted reasoning with store:false. The SDK removes the opaque reasoning when it resumes a session. Write this as a known limitation.

Spike evidence

A live probe added instruments to the true event loop of turn_runner (COPILOT_SPIKE_TRACE=1). The probe sent two turns through the gateway to claude-sonnet-4.6, with reasoning_effort=high and a get_weather tool. The probe captured the raw order of the copilot.SessionEvent values. After that, the work removed the instruments again.

FindingEvidenceConsequence
The reasoning streams in increments AssistantReasoningDeltaData{DeltaContent, ReasoningID} — 36 deltas, then 38 deltas, in two turns. A live delta.reasoning is possible. The loop only has no case for it today.
The interleaved thinking through the tools is true Turn 2 writes a new reasoning block, with a different ReasoningID, before its message and after the tool result. The usual Chat loop with more than one request keeps this automatically. A special transport is not necessary.
The opaque or encrypted thinking is available AssistantMessageData.ReasoningOpaque != nil on every turn. It is an Anthropic signature blob. reasoning_details with signed or encrypted continuity is possible, and not only plain text.
In a turn: the reasoning, then the text, then the tool The reasoning deltas stop before AssistantMessageStart. The tool request is in the final message. Write the reasoning chunks before the content chunks and the tool chunks. This is the split pattern of Ollama.
AssistantStreamingDeltaData has no data value It carries only TotalResponseSizeBytes. It is a heartbeat with a count of the bytes. Ignore it in the code. Do not use it as content.

Wire contract

The order of the SSE chunks gives all the order between the reasoning deltas, the content deltas and the tool-call deltas. The reasoning continuity makes a round-trip: the client replays the assistant message, with its reasoning fields, before the tool results. OpenRouter, DeepSeek and Ollama give the same mechanism in their documents.

Implementation phases

The internal event model — capture and stream the reasoning

Change the one point where the code drops the reasoning. This is the prerequisite for every change to the wire.

  • In internal/copilotgw/turn_runner.go, add case *copilot.AssistantReasoningDeltaData. It writes a new internal event for a reasoning delta.
  • On AssistantMessageData, capture ReasoningText, ReasoningOpaque and EncryptedContent into new fields of TurnResult.
  • Ignore AssistantStreamingDeltaData in the code. It is a heartbeat.
  • In internal/copilotgw/types.go, add StreamEvent{Kind:"reasoning_delta", Delta, ReasoningID}. Add the reasoning fields and the opaque fields to TurnResult.

The OpenAI wire types — the reasoning fields

Add the usual fields and a structured detail type. Accept these fields when they come in, and do not give an error.

  • In internal/openai/types.go, add reasoning, reasoning_content and reasoning_details []ReasoningDetail to the assistant message and to the chunk delta.
  • Make ReasoningDetail{Type, Text, Signature, Data, Summary, ID, Format, Index}. Use omitempty semantics for each type.
  • Parse the reasoning of an assistant message that comes in, and do not give an error. Accept reasoning, reasoning_content and reasoning_details.

The Chat Completions encoder — interleave and collect

This is the primary interface. Stream the reasoning before the content deltas and the tool deltas. Attach the full reasoning to the final message.

  • In internal/httpapi/chat.go, control reasoning_delta. Write delta.reasoning chunks, and delta.reasoning_content chunks, before the content deltas and the tool deltas. This is the split pattern of Ollama.
  • On the last message, fill reasoning, reasoning_content and reasoning_details, with content and tool_calls.
  • Connect the control for the emission policy: both (the default), reasoning, reasoning_content or off.

Validation — accept the parallel tool calls

Remove the artificial refusal. Keep the validation of the structure.

  • In internal/openai/validation.go, remove the Chat refusal of parallel_tool_calls=true.
  • Check that the behavior of the toolproxy batch with more than one call, and of Broker.FindByCallIDs, is unchanged. Add a regression test.

The Responses interface — ordered reasoning items

A mapping with more fidelity for /v1/responses.

  • In internal/httpapi/responses_stream.go, write ordered reasoning output items and reasoning stream events, with the function_call items.
  • Put the content that is equivalent to reasoning_details into the reasoning item. Use content, and encrypted_content when it is present.
  • Keep the order of the items, and keep the stable IDs from the ReasoningID of the SDK.

The hydration of the history and the continuation

Make the round-trip keep all the data, and do not depend on the client.

  • In internal/hydration/hydration.go, accept the assistant reasoning that comes in. Replay it only when the code builds a cold session or a stateless session again.
  • Use the live Copilot session for the continuity. Never give a 400 for the reasoning that a client sends.
  • Write that the portable round-trip of the encrypted reasoning with store:false is not supported. The SDK removes the opaque reasoning when it resumes a session.

The tests, the documents and the configuration

Make the behavior stable, and show the new controls.

  • Unit tests: the mapping of a reasoning delta, the collection into the final message, the shape of reasoning_details, the acceptance of the parallel tool_calls, and the control for the emission policy.
  • Make the temporary probe a live test with a condition (COPILOT_API_LIVE_TESTS=1). The test must show that the reasoning deltas come before the content.
  • The compatibility matrix of the README, and a new environment variable for the emission policy.

Testing plan

Deterministic (unit)

  • Give a false sequence of SDK events. Check that the code writes the reasoning_delta events, then the content, then the tool_calls.
  • The final message carries reasoning, reasoning_content and reasoning_details.
  • The code accepts the reasoning that comes in. Test the replay path for a cold history.
  • The code accepts parallel_tool_calls=true. The batch with more than one call stays complete.

Live (with a condition)

  • The reasoning streams as deltas before the content. Use claude-sonnet-4.x with reasoning_effort high.
  • The second turn makes a new reasoning block after a tool result.
  • ReasoningOpaque is present, and the code puts it into reasoning_details.

Risks and problems

The client shows the reasoning two times. Some clients draw reasoning and reasoning_content. Write both by default. But release the control that makes the output smaller, and test with Open WebUI, Jan, OpenCode and Pi.
The opaque reasoning is bound to the session. The SDK removes ReasoningOpaque and EncryptedContent when it resumes a session. A portable stateless continuity needs an encryption envelope of our own. That is not in the scope of v1. Write the limitation in the documents.
The providers change. vLLM changed reasoning_content to reasoning. Keep an adapter layer. Do not put one field name in the code.
The client does the tool execution. The tool handler of the SDK gives success=false for the client tools that wait. This is correct behavior. The thinking between the tools occurs between the HTTP requests, and not in one stream.

Acceptance criteria

Must be in the release

  • The Chat stream writes ordered reasoning deltas before the content deltas and the tool deltas.
  • Chat with no streaming attaches reasoning, reasoning_content and reasoning_details.
  • The interleaved thinking stays through the loop of the tool calls.
  • Chat accepts parallel_tool_calls=true.
  • The control for the emission policy has a good default with the maximum compatibility.
  • The deterministic tests and the live test with a condition pass. The README is up to date.

Can come later

  • The ordered reasoning items of Responses (Phase 5), if it is planned separately.
  • The portable round-trip of the encrypted reasoning with store:false.
  • The normalization of reasoning_details for formats other than Anthropic.
Definition of done: a Chat Completions client gets streamed, ordered reasoning between the tool calls. The client can replay it for the continuity. The client sees coherent interleaved thinking through a tool loop with more than one step. The compatibility matrix of the README gives this behavior, and the deterministic tests and the live tests with a condition cover it.
