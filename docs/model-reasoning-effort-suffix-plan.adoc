= Model Reasoning-Effort Suffix Implementation Plan
:toc: left
:toclevels: 3
:sectnums:

== Summary

Add a model-selector syntax for the OpenAI interface. The syntax lets a request put the reasoning effort in the `model` string:

[source,json]
----
{
  "model": "gpt-5.6-sol:xhigh"
}
----

The proxy reads this as the canonical Copilot model `gpt-5.6-sol` with the explicit reasoning effort `xhigh`. The proxy uses only the canonical model ID for the model lookup, the capability checks, the configuration of the Copilot SDK session, the storage and the continuation identity.

A model name with no suffix, such as `gpt-5.6-sol`, stays unchanged. It does not make an explicit request effort. It continues through the existing path for the default effort. That path uses `COPILOT_DEFAULT_REASONING_EFFORT` when the value is configured and applicable. If not, it uses the default of the model or of the provider.

== Goals

* Accept model selectors with a suffix on Chat Completions requests and on Responses requests.
* Cover non-streaming requests, SSE streaming requests, Responses WebSocket requests, and WebSocket warm-session requests that use `generate:false`.
* Make a suffix operate like the existing explicit `reasoning_effort` request field.
* Remove the suffix before the exact model validation, and before the proxy sends the model to the Copilot SDK.
* Keep the current behavior for a model with no suffix and for a configured default.
* Keep the canonical model identity in tool continuations, in warm sessions, in stored responses, in image capability checks, and in model-cache lookups.
* Return errors in the OpenAI shape for a malformed selector and for contradictory effort inputs. The errors must be deterministic.
* Show `model:effort` aliases in `GET /v1/models` for every effort that each canonical model announces.

== Non-goals

* To change how the code rounds a configured default effort to a value that the model supports.
* To add stricter model-capability validation for an explicit effort. The existing explicit `reasoning_effort` path sends a normalized value and does not round it.
* To configure again the effort of a Copilot session that runs, during a live tool continuation.
* To store both a requested alias and a canonical model ID.

== Existing Behavior and Constraints

=== Request surfaces

The feature must cover all the entry points for generation:

* `internal/httpapi/chat.go` decodes and prepares Chat Completions HTTP.
* `prepareResponseRequest` in `internal/httpapi/responses.go` prepares Responses HTTP.
* `internal/httpapi/responses_ws.go` also calls `prepareResponseRequest` for the Responses WebSocket. Normalization in that function covers flat `response.create` payloads, nested `response.create` payloads and warm requests.

The request types already have a separate `Model` field and a separate `ReasoningEffort` field in `internal/openai/types.go`. The decoding of Responses HTTP and the decoding of the WebSocket already come together in `ResponsesRequestFromFields` in `internal/openai/responses_decode.go`. Thus the control of the suffix must be a request policy that the code applies after the decode operation. Do not write the same code again in the JSON decoders.

=== Exact model identity

`RealGateway.findModel` does an exact match of the model ID in `internal/copilotgw/images.go`. If the code sends `gpt-5.6-sol:xhigh` through unchanged, the model cache misses. The code can then do a forced refresh that is not necessary, and it gives `model_not_found`.

The canonical model strings are also used by:

* The Chat model validation and the Responses model validation in `internal/copilotgw/chat.go` and `internal/copilotgw/responses.go`.
* The configuration of the SDK session, for the create operation and the resume operation, in `internal/copilotgw/sessions.go`.
* The image capability checks and the image limit checks.
* The comparison of the model of a pending tool batch in `internal/copilotgw/continuations.go`.
* The match of a warm Responses session in `internal/copilotgw/warm_response.go`.
* The metadata of a chat session and the stored Responses records.

The code must do the normalization before all of these operations.

=== Existing effort resolution

`internal/copilotgw/models.go` currently separates two behaviors:

. The code trims an explicit request effort, changes it to lowercase, and sends it directly.
. If the request effort is absent, the code can use `COPILOT_DEFAULT_REASONING_EFFORT`. The code makes this value agree with the model metadata when the metadata is available.

The suffix belongs to the first category. The code must not treat the suffix as a configured default, and must not round it to the nearest effort that the model announces.

The values that have a rank now are `none`, `minimal`, `low`, `medium`, `high` and `xhigh`. But the code does not limit an explicit request field to that set. The reasoning capabilities and the effort lists of a model can change.

== Recommended Contract

=== Selector grammar

Parse the last colon in a model string that is not empty:

[source,text]
----
<canonical-model-id>[:<reasoning-effort>]
----

The rules are:

* If there is no colon, the model has no suffix and the request gets no effort from a suffix.
* The last colon divides the model ID and the effort. Thus the earlier colons stay available for a future base ID that includes the provider.
* The base model and the suffix must both be not empty after the code finds the separator.
* Do not trim the base model ID, and do not change its case.
* Trim the space characters around the effort, and change the effort to lowercase. This agrees with the current behavior of the gateway.
* Refuse a suffix that is empty or that has only space characters. Give an `invalid_request_error` on `model`.
* Do not put the six ranked values in the parser as a permitted list. Any suffix that is not empty gets the same meaning as the existing explicit `reasoning_effort` field. The validation of the model or of the provider stays the authority.
* The colon is now reserved as the separator of the suffix at the OpenAI boundary. Thus, if upstream model IDs that end with `:<value>` are introduced, a future mechanism for escape or for versions must control them.

The examples are:

[cols="1,1,1",options="header"]
|===
|Input `model`
|Canonical model
|Suffix effort

|`gpt-5.6-sol`
|`gpt-5.6-sol`
|absent

|`gpt-5.6-sol:xhigh`
|`gpt-5.6-sol`
|`xhigh`

|`vendor:model:HIGH`
|`vendor:model`
|`high`

|`gpt-5.6-sol:`
|error
|error
|===

=== Effort source precedence and conflicts

Treat all the effort forms that the request gives as different spellings of one explicit value:

* the model suffix;
* the top-level `reasoning_effort`;
* the Responses `reasoning.effort`.

Normalize each value that is not empty, then compare the values. If more than one form is present:

* accept the forms when they normalize to the same value;
* refuse the request when the values are different;
* do not let one spelling replace another one without a message.

This makes the existing Responses conflict policy larger. It does not add a second rule for precedence. A request that has only a suffix fills the same internal explicit-effort value that the top-level `reasoning_effort` fills.

If the model has no suffix and the request has no effort, leave the explicit effort empty. Then the existing path for the configured default or the model default stays in control.

=== Canonical identity and observable output

Use the canonical base model everywhere after the code normalizes the request:

* the gateway requests;
* the `model` attribute of the logs;
* the `model` fields of the Chat completion and of the Chat stream;
* the Responses objects and the stream events;
* the stored session records and the stored response records;
* the comparisons of a tool batch and of a warm session.

Log the value from the suffix in the existing `reasoning_effort` field. This keeps one stable model identity. It also prevents a new field for the requested model or for the display model through the gateway layer and the storage layer.

`GET /v1/models` lists each canonical upstream model ID. It also lists a virtual `<model>:<effort>` alias for every normalized value in `supported_reasoning_efforts`. If `default_reasoning_effort` is announced but is not in that list, the list includes its alias also. The alias entries keep the canonical capability metadata, but not `supported_reasoning_efforts` and `default_reasoning_effort`. Those two apply only to the canonical entries. Thus an alias is a terminal choice with a fixed effort, and it does not look like a recursive selector. The generation responses and the logs continue to show only the canonical model ID.

== Proposed Design

=== Shared parsing and merge helpers

Add pure helpers in `internal/openai`, near the request validation. The suffix is compatibility syntax for the OpenAI interface, and it is not a Copilot model ID.

A suggested shape is:

[source,go]
----
type ModelSelector struct {
    Model           string
    ReasoningEffort string
    HasEffort       bool
}

func ParseModelSelector(raw string) (ModelSelector, error)

func MergeReasoningEffort(
    suffix ModelSelector,
    explicit string,
    explicitParam string,
) (string, error)
----

The API can be different, but the helper must:

* have no dependency on the gateway or on the model catalog;
* return a canonical model and an optional normalized effort;
* give `openai.InvalidRequest` errors with stable parameter names;
* compare the effort values after it trims them and changes them to lowercase;
* leave a model with no suffix unchanged, and leave an absent effort unchanged.

Keep the parse operation separate from the change of the request type. Then table tests can cover the full contract.

=== Chat Completions boundary

In `internal/httpapi/chat.go`:

. Decode `ChatCompletionRequest` as the code does today.
. Parse `req.Model` immediately after the decode operation and before `ValidateChatRequest`.
. Merge an effort from the suffix with `req.ReasoningEffort`.
. Replace `req.Model` with the canonical model. Set `req.ReasoningEffort` to the merged explicit value.
. Continue through the existing validation, the instruction folding, the continuation detection, the effort resolution, the logging and the gateway construction.

Do this before the branch for the tool continuation. Then a live continuation and a cold-fallback continuation both compare and hydrate with the canonical model. A session that the code made with the suffix already has that effort in its SDK configuration. The subsequent live tool results continue that session with the existing continuation semantics.

=== Responses HTTP and WebSocket boundary

At the start of `prepareResponseRequest` in `internal/httpapi/responses.go`:

. Parse `req.Model` and make it canonical.
. Merge an effort from the suffix into the top-level `req.ReasoningEffort`.
. Check the request. This includes the comparison with the nested `reasoning.effort`.
. Find the final explicit effort with `ResponsesReasoningEffort`.
. Continue through the existing tool normalization, the input parse operation, the continuation detection, the default resolution, the logging fields and the creation of the gateway request.

Change `validateResponsesReasoning` in `internal/openai/validation.go`. The code must check the equality of the top-level value and the nested value after the same trim operation and the same change to lowercase. This lets equivalent forms pass, such as `model: "gpt-5:XHIGH"` with `reasoning.effort: "xhigh"`. The code still refuses a true conflict.

Both Responses transports use `prepareResponseRequest`. Thus this one boundary covers:

* HTTP with no streaming;
* HTTP SSE streaming;
* the flat WebSocket `response.create`;
* the nested WebSocket `response.create.response`;
* the WebSocket warm creation with `generate:false`, and the later use of the warm session.

=== Gateway contract

Keep the request structures of `internal/copilotgw` unchanged. Their contract stays:

* `Model` is always a canonical Copilot model ID;
* `ReasoningEffort` is the normalized explicit request value, or it is empty;
* `DefaultReasoningEffort` is still a separate field;
* `ResolvedReasoningEffort` is used for the preflight optimization and the logging optimization, as it is today.

Do not add the parse operation of the suffix to `findModel` only. That corrects the lookup, but the alias still goes into the session configuration, the hydration, the continuation comparisons, the responses and the storage. The direct callers of the gateway must continue to give canonical internal requests.

=== Continuation behavior

The code makes the model canonical before the continuation branches. Thus an initial `gpt-5.6-sol:xhigh` request and a repeated selector with a suffix compare as the model `gpt-5.6-sol`.

The implementation must keep the existing rule: a live pending tool turn continues the SDK session that is already configured. A change of the requested effort during that live continuation is not a supported operation. The documentation must tell clients to keep the model selector stable through a tool loop. The cold fallback paths use the parsed explicit effort when they make a replacement session. The existing explicit `reasoning_effort` values operate in the same way.

A later change can make the code store the resolved effort on the pending batches, and refuse an attempted change during a continuation. That change is not necessary to add the suffix syntax. Do not put it in this change without a dedicated compatibility review.

== Implementation Steps

=== Phase 1: Parser and normalized conflict handling

. Add the parser of the model selector and the helpers for the effort merge and the effort normalization, under `internal/openai`.
. Add table-driven unit tests in `internal/openai/validation_test.go`, or in a focused `model_selector_test.go`.
. Change the comparison of the top-level conflict and the nested conflict in Responses to use the common normalized comparison.
. Keep the explicit suffix values dependent on the model. Do not add a new global rule for enum validation.

=== Phase 2: HTTP request integration

. Normalize the Chat requests immediately after the decode operation in `internal/httpapi/chat.go`.
. Normalize the Responses requests at the start of `prepareResponseRequest` in `internal/httpapi/responses.go`.
. Make sure that the calls to `resolveGenerationReasoningEffort` use the canonical model and the merged explicit effort.
. Make sure that the generation logs give the canonical model and the `reasoning_effort` that comes from the suffix.
. Do not change the JSON decoders in `internal/openai/types.go` and `internal/openai/responses_decode.go`. You can add the test fixtures that show the parity of the transports.

=== Phase 3: Regression coverage across transports and stateful flows

. Make the capture-gateway tests in `internal/httpapi/server_test.go` larger, for Chat and for Responses.
. Add Responses WebSocket tests for the flat request shape and for the nested request shape.
. Cover the `model` fields of the streaming responses and of the non-streaming responses.
. Cover the preparation of the Chat tool continuation and of the Responses tool continuation with a repeated suffix.
. Cover the creation and the use of a warm Responses session with a selector that has a suffix.
. Check that the malformed forms and the conflicting forms return errors in the OpenAI shape, and that they do not call the gateway.
. Add or change the tests in `internal/copilotgw` only where it is necessary. The tests must show that the downstream requests stay canonical. Do not teach the gateway to parse an alias.

=== Phase 4: Documentation and integration validation

. Change the Models row and the Reasoning effort row of the compatibility matrix in the README.
. Add examples of the suffix syntax and of a conflict to the Reasoning effort section.
. Write that a model with no suffix keeps the behavior of the default resolution.
. Write that `/v1/models` lists the canonical IDs and the terminal effort aliases. The aliases keep the capability metadata that is not a choice.
. Write that the `model` fields of the responses and the logs use the canonical model.
. Add an integration case for the Deno AI SDK. The case selects `model + ":" + effort` and does not give `providerOptions.openai.reasoningEffort`. This shows the compatibility use case for clients that have no effort field.
. Change `tests/ai-sdk-deno/README.md` if the behavior of the live test or the guidance for the environment variables changes.

== Test Plan

=== Parser unit tests

Use a table that covers:

* a model with no suffix and no effort;
* `none`, `minimal`, `low`, `medium`, `high` and `xhigh`;
* mixed case and space characters around the effort;
* a base ID that contains an earlier colon;
* an empty base;
* a suffix that is empty or that has only space characters;
* a suffix with no base;
* a suffix and a top-level effort that agree after the normalization;
* a suffix and a top-level effort that do not agree;
* a suffix and a nested Responses effort that agree, and a pair that does not agree;
* any future effort value or model-specific effort value that is not empty.

=== HTTP and WebSocket tests

Check that:

* Chat with streaming and Chat with no streaming send `gpt-5.6-sol` and `xhigh` to the gateway;
* the Chat wire responses and the Chat chunks show the canonical model;
* the Chat tool continuations do the normalization before the gateway call and before the comparison of the batch model;
* Responses HTTP with no streaming and Responses SSE send the canonical model and the explicit effort;
* the flat WebSocket payload and the nested WebSocket payload of Responses operate in the same way;
* the WebSocket warm creation with `generate:false` and the later generation keep the match of the canonical model and of the effort;
* a model with no suffix still sends an empty explicit effort, and sends the configured default separately;
* effort spellings that do not agree return HTTP 400, or a WebSocket `invalid_request_error` frame with a stable parameter;
* malformed selectors fail before the model-cache lookup and before the generation;
* the logging tests see the canonical `model`, the explicit `reasoning_effort`, and any value that the code resolved separately.

=== Gateway and persistence regression tests

Make sure that the existing tests still show that:

* the exact model lookup gets the base ID;
* an explicit effort does not go through the rounding of the configured default;
* an absent effort still uses the current logic for the closest supported default;
* the warm sessions compare the canonical model and the normalized effort;
* the pending batches and the stored response records contain canonical model IDs;
* the image capability checks use the base model.

== Acceptance Criteria

. `model: "gpt-5.6-sol:xhigh"` comes to the Copilot SDK as the model `gpt-5.6-sol` with the explicit reasoning effort `xhigh`.
. The behavior is the same for Chat Completions, for Responses HTTP and for Responses WebSocket.
. The streaming path and the non-streaming path both operate correctly.
. A `gpt-5.6-sol` with no suffix and with no request effort leaves the explicit effort empty, and keeps the existing default behavior.
. A suffix has the semantics of an explicit request. The code does not round it like a configured default.
. The code accepts a suffix, a top-level effort and a nested Responses effort that agree after the normalization.
. The code refuses effort forms that contradict each other. It does this in a deterministic way, and not with a replacement that has no message.
. The code refuses a form with an empty base or an empty suffix. It gives an invalid request in the OpenAI shape.
. The exact model validation, the model metadata lookup, the SDK configuration, the continuation identity, the response storage and the image checks get only the canonical model ID.
. The responses and the logs show the canonical model and the selected reasoning effort.
. `/v1/models` keeps the canonical entries and their reasoning metadata. It adds normalized aliases for every effort that a model announces, with no duplicates. The aliases do not have the supported-effort metadata or the default-effort metadata.
. The existing tests for the default resolution, the reasoning output, the continuation, the warm session and the transports still pass.
. The README gives the syntax, the precedence and the conflicts, the canonical echo behavior, the behavior of the model list, and the expectations for a continuation.

== Risks and Mitigations

[cols="1,2",options="header"]
|===
|Risk
|Mitigation

|A future upstream model ID contains a colon.
|Parse only the last colon. Write that the suffix grammar reserves the colon. Keep the parse code isolated, so that an escape mechanism or a version mechanism can come later.

|A future effort value is not in the ranked set of today.
|Accept any suffix that is not empty. This agrees with the current behavior of the explicit field. Leave the validation of the model support or the provider support as the authority.

|An incorrect suffix comes to the provider.
|Return local errors for malformed empty forms and for conflicts. Write that the values that are not empty depend on the model, as the explicit fields already do.

|The canonical echo is not what a client that expects the alias waits for.
|Write the contract of the canonical echo. Test it in the same way in Chat, in Responses, in SSE, in WebSocket, and when a client gets a stored response.

|The alias expansion makes a larger model list. The upstream metadata can contain the same effort with a different spelling.
|Keep the canonical entries first. Normalize the effort aliases and remove the duplicates. Do not put the reasoning metadata for a choice in an alias, but keep the other canonical capabilities.

|A client changes the effort during a live tool continuation.
|Write that the selector must stay stable through a tool loop, and keep the session that is already configured. A later feature can add the validation of the effort at the batch level.

|The normalization becomes different in HTTP and in WebSocket.
|Use `prepareResponseRequest` again, and test the flat WebSocket payload and the nested WebSocket payload.
|===

The expected files for the first implementation are:

* `internal/openai/validation_test.go`, or a new `internal/openai/model_selector_test.go`
* `internal/httpapi/chat.go`

* `README.md`
* `tests/ai-sdk-deno/ai_sdk_integration_test.ts`

A change to the storage schema, to the request types of the gateway, or to the model cache is not necessary. The handler of `/v1/models` expands the canonical gateway models into alias entries for the OpenAI interface. It does not change the catalog of the gateway.
