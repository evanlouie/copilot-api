Implementation plan · Responses API · Dynamic tool search

Install tool_search results at a clear SDK turn boundary

This is a plan for Option B. When Codex returns loadable tool specifications in tool_search_output.tools, the proxy merges them into the tool catalog of the Responses request. The proxy then continues in a new Copilot SDK turn. Deferred tools such as multi_agent_v1.spawn_agent then become callable, and copilot-api does not become a tool runtime.

Summary

Codex can call tool_search now, and it can return loadable tool specifications. But the proxy only checks these specifications and records them as output text. The proxy does not install them into the active tool catalog of the Copilot SDK session. This causes the failure that we see with the sub-agents. Codex finds multi_agent_v1.spawn_agent, wait_agent, send_input, resume_agent and close_agent. The model cannot call them in the next step, because the SDK turn still has the old tool set.

Method: make tool_search_output a catalog boundary. Do these steps when a live search output contains valid loadable tools. First, check the ownership and check that a merge is possible. Then store the search output from the client as continuation transcript state. Then stop the old parked SDK turn, and do not show results that come from the old catalog. Last, start one model turn only, with a new RequestTools instance that you build from the merged catalog.

The proxy gives these loaded tools to the model, and returns their calls to the Codex CLI. The Codex CLI continues to run the tools. copilot-api must not run sub-agents, MCP actions, shell commands, or other tool logic that the client owns.

The problem now

The implementation has the necessary parser and the necessary safety controls. It does not have the dynamic catalog step:

  • The proxy gives tool_search_call to the model as a tool that the client owns.
  • The proxy parses tool_search_output. It checks the tools array as loadable function specifications or namespace specifications.
  • The proxy does not merge the returned specifications into ResponseRequest.Tools for the next SDK turn.
  • The live parked SDK handler gets a string output only. The Tools field and the AvailableTools field of the session do not change.
  • If you complete that parked handler, the old runner continues to plan with the old catalog. This occurs if the implementation does not replace the old runner.
  • The warm sessions and the stored response records do not contain the catalog change that the tool search makes.
The effect that we see: the model can speak about the tools that the search result gives. But when the model tries to call multi_agent_v1.spawn_agent, that tool is not in the callable set that the SDK has.

Goals and non-goals

Goals

  • Install valid tools from tool_search_output.tools for the next planning step of the model.
  • Support deferred namespace tools, for example multi_agent_v1.spawn_agent.
  • Keep the canonical Responses names and the namespaces in the output items.
  • Store sufficient catalog state for the later continuations, for the warm sessions and for the fallback after a restart.
  • Keep the SDK in ModeEmpty. Give it only the synthetic custom tools of the current request.

Non-goals

  • Do not run sub-agent tools in copilot-api.
  • Do not enable the built-in Copilot SDK tools for MCP, shell, files, memory, skills, repositories or host git.
  • Do not implement the hosted OpenAI tools: the web search of the provider, the file search, the image generation and the code interpreter.
  • Do not change the active SDK tool list during a turn. Do this only if the SDK gets a supported API for it.

Architecture

The dynamic sequence becomes this: search → check the active outputs → merge the catalog → store the transcript and the catalog → stop the old runner → configure the SDK again → continue.

Turn N SDK catalog
  └─ tool_search
       ↓ model calls tool_search
Responses output
  └─ tool_search_call(call_search)
       ↓ Codex executes search and returns tools
Continuation input
  └─ tool_search_output(call_search, tools: [namespace multi_agent_v1 ...])
       ↓ proxy validates active outputs, status, ownership, allowlisted fields, and collisions
Merged catalog
  ├─ original function/custom/namespace tools
  ├─ tool_search
  └─ loaded namespace multi_agent_v1.*
       ↓ old runner is aborted/drained; new synthetic or proven-safe resumed SDK turn is configured with merged catalog
Turn N+1 model can call multi_agent_v1__spawn_agent
       ↓ proxy rehydrates
Responses output
  └─ function_call(namespace: "multi_agent_v1", name: "spawn_agent")
Important boundary: the new tools become callable only after you configure a new SDK turn with the merged catalog. The implementation must never say that the returned tools were callable before Tools and AvailableTools contain them.

Implementation phases

Phase 1

Make one canonical module for the tool catalog

Make one module that controls the normalization, the merge, the aliases, the collision checks, the semantic keys and the conversion to the storage DTO.

  • Add a ToolCatalog type around the canonical Responses tool specifications. Do not use the raw SDK aliases.
  • Give these operations: FromRequest, FromStored, MergeLoaded, Flatten, Key, StoredDTO and WithoutRaw.
  • Move the double logic for the SDK-safe aliases and for the collisions out of openai and out of toolproxy. Put it in this module or in a shared helper.
  • Keep the history data, for example the call_id of the source search, out of the semantic key of the catalog. Include it only when you compare the audit history on purpose.
  • Make sure that the catalog keys ignore the byte order and the spaces of the raw JSON. The keys must keep the schema, the format, the strictness, the deferred loading, the namespace, the execution and the descriptions.
  • Show “the catalog is absent from a migrated record” and “the catalog is known and empty” as two different conditions.

Phase 2

Define safe stored DTOs and data limits

Do not use the internal Go structures with their temporary fields as the durable schema.

  • Increase sessionstore.ResponseRecordVersion.
  • Add these JSON DTOs: StoredToolCatalog, StoredToolSpec, StoredLoadedToolEvent and StoredToolOutput.
  • Store the canonical Responses identities and the schema fields and format fields that have a meaning. Do not use the stored SDK aliases as the primary data.
  • Store the raw returned tool_search_output.tools only where the transcript needs them. The default catalog storage is WithoutRaw.
  • Set a limit on the number of loaded tools, on the schema bytes of each tool, on the total catalog bytes, on the depth of the structure and on the length of a description. Apply the limits before storage and before you give the tools to the SDK.
  • Log the catalogs of the loaded tools as counts and canonical names only. Do not log the full schemas or the full descriptions. Log them only under the current policy for content logging and truncation.
  • Write in the documentation that a dynamic catalog can contain sensitive tool descriptions and schemas. The proxy keeps them locally until a purge. This includes the continuation state and the debug state for store:false.
Phase 3

Parse the returned tools into typed continuation outputs with an allowlist

Do not keep tool_search_output.tools as raw JSON only after the check.

  • Add a typed field to the internal carrier of the continuation output. Use LoadedTools []NormalizedTool, LoadedCatalogDelta or an equivalent field.
  • Make an allowlist of the fields for the returned function specifications and namespace specifications. Reject or remove the unknown fields of a hosted provider. Examples are server_url, server_label, the authentication configuration and the provider configuration, the hints for hosted execution, and each hosted tool for the web, for files, for code or for images that has the type of a tool that the client owns.
  • Reject these items: a returned custom tool, a nested tool_search, a hosted tool, an MCP declaration that the provider hosts, a nested namespace, an incorrect schema, a collision with the sentinel, a duplicate identity and a collision of the SDK aliases.
  • Install the loaded tools only when the matched pending call is a live tool_search call with execution: "client". The status value must be absent, success or completed.
  • If status is failed, incomplete, cancelled or unknown, record the search output but do not install the tools that come with it. Reject the request if the client sends a failed status together with loaded tools. Accept it only if you select a mode that installs nothing.
  • Record the source call_id, the response id, the raw payload of the tools, the normalized loaded tools and the merge result. Use this data for the audit and for the replay.
Phase 4

Find the effective catalog for each continuation

A continuation needs one known catalog source before an SDK turn starts.

  • For an initial request, use the normalized catalog of the request. Store it as the installed catalog.
  • For a request with previous_response_id, start from previousRecord.InstalledToolCatalog if it is present.
  • For a migrated record with no catalog state, use the tools of the current request only if the client sends them. If not, mark the replay of the loaded tools as not available. Give a clear error if a dynamic loaded tool is necessary.
  • Merge the active tool_search_output.LoadedTools into the previous installed catalog. Do this before you complete or cancel the live batch.
  • Define the behavior of a repeated search. An identical tool that is installed causes no change. An exact semantic duplicate is accepted and does nothing. A definition that conflicts causes a rejection. More than one search output in one batch merges in the order of the call_id values.
  • Process an empty tools array as a successful search that does not change the catalog.
  • Obey an effective tool_choice: "none" on a continuation. Give no installed tool to the model, and give the sentinel only. Do this also when a loaded catalog exists.
Phase 5

Make one shared planner for the continuations

One planner at the level of the gateway controls the non-streaming HTTP path, the streaming HTTP path, the WebSocket path and the warm-session path.

  • Take these inputs: the parsed outputs, the metadata of the request, the optional warm session, the previous response record and the lookup of the live batch.
  • Return one decision: a usual continuation with the parked handler, a change of the runner after a tool search, a cold synthetic fallback, the creation of a warm response, or a clear error for a request that the proxy does not support.
  • Take previous_response_id from the live batch if the client does not send it. Give the continuation response id one time only.
  • Select the active outputs from the current live batch. Keep the old outputs of the stateless history for the reconstruction of the transcript only.
  • Check the model, the ownership of the previous response, the kind of the endpoint, the kind of the call, the optional name of the custom output, the status and the execution of the search, and the exact number of the outputs. Do these checks before you change a live batch.
  • Make sure that the non-streaming code and the streaming code save the same final response records and the same ownership of the pending batch.
Phase 6

Replace the old runner

The dynamic branch must not let the old runner with the old catalog make a turn after the search that the client can see.

  • Check the active outputs and merge the loaded catalog. Do this before you complete, cancel or remove the batch.
  • Store the tool_search_output of the client in a structured continuation transcript or log. Do not store it as an assistant output item that the API shows.
  • Default implementation: cancel the old runner, disconnect it, remove the broker batch, forget the pending runner, and discard each late result of the old runner.
  • Do not use the usual CompleteToolOutputsWithSetup path for the search outputs that contain loaded tools. Use it only if a controlled integration test shows two facts. The SDK can record the tool result. The SDK can then continue safely with the replaced tools before it plans with the old catalog.
  • Check that there is no second final response, no old runner in memory and no live batch left after the change of the runner.
Use the synthetic replacement by default: the resume operation of the SDK must first show that it can replace the tools safely after a delivered tool result. Until then, build the continuation after the search from the stored transcript state. Use a new synthetic SDK turn that has the merged catalog.
Phase 7

Build the replay prompts for the synthetic mode and for the resumed mode

Continue. is sufficient only when the same SDK session contains the full previous conversation and the accepted tool result.

  • For the synthetic replacement, include this content: the previous user transcript and assistant transcript, the assistant tool_search_call, all tool outputs of the active batch, the returned tool specifications or a short note about their availability, and each user text that comes after the outputs.
  • For a resume in the same session that is proven safe, use a short continuation prompt. Use it only after the SDK records the tool result and after the new catalog is installed.
  • Keep the response.output that the API shows as assistant outputs only. Store the continuation inputs and the tool outputs of the client in separate transcript fields.
  • Put the canonical names in the notes of the transcript. Do not put the SDK aliases in a prompt, except for debug work under explicit content logging.
  • Keep the namespaced function calls, the custom inputs, the arguments of the tool search, the status and the execution of the tool search, and the summaries of the raw returned tools in the cold fallback.
Phase 8

Add the support for the transports in steps

Do the transports in an order. Each path must have a clear proof before you use it for all the traffic.

  • First: the non-streaming POST /v1/responses. Use a fake SDK and a fake provider that record the merged Tools and AvailableTools.
  • Second: the HTTP SSE streaming. Use the same planner decision and stable lifecycle events.
  • Third: the WebSocket response.create. Use the same planner at the level of the gateway and the same rules for the sequence numbers.
  • Fourth: the warm sessions with generate:false. Define what occurs when generate:false comes with tool-output continuations. Either the merge planner prepares the turn after the search, or the request fails with a clear error until the proxy supports it.
  • If a transport is not complete in the first part of the implementation, add a temporary control that gives a clear error. Do not go back to the old catalog without a message.
Phase 9

Make the safety boundaries stronger

The installation of the tools that the search finds must not weaken the rule that the proxy runs no tool.

  • Keep ModeEmpty.
  • Keep the SDK runtime defaults. The MCP servers, the skills, the operations on the shell, the files, the repository and the memory, the host git operations, the sub-agent streaming and the session store stay disabled.
  • The permissions approve only the exact SDK names that come from the merged catalog of the current request.
  • Reject each SDK tool request that is not in the catalog of the current request.
  • Do not install a hosted tool or a proxy-run tool that tool_search_output.tools returns.
  • The tests must show that copilot-api starts no sub-agent process, no shell command, no MCP server, no file tool and no SDK built-in tool because of a dynamic installation.
Phase 10

Proof with the Codex sub-agents, and the documentation

Show that the failure is corrected. Do not depend on model output that changes between the runs.

  • Use a fake SDK and a fake provider. They send a call to a loaded tool only when the merged catalog contains multi_agent_v1__spawn_agent.
  • Check that the proxy returns that call with namespace: "multi_agent_v1" and name: "spawn_agent".
  • Keep the Codex CLI as a manual test that does not block the build. The steps are: find multi_agent_v1, call a sub-agent operation that makes no change, wait, and close.
  • Update the README when the automatic installation after the search is complete. Remove the current limitation. That limitation says that the returned tools need a later request with an installed catalog.

Proposed data model

type ToolCatalog struct {
    Tools []CanonicalToolSpec // the SDK aliases do not control the data

    SchemaVersion int              `json:"schema_version"`

    KnownEmpty    bool             `json:"known_empty,omitempty"`
}

type StoredLoadedToolEvent struct {
    SourceCallID string            `json:"source_call_id"`
    ResponseID   string            `json:"response_id"`
    Status       string            `json:"status,omitempty"`
    Execution    string            `json:"execution,omitempty"`
    RawTools     json.RawMessage   `json:"raw_tools,omitempty"`
    LoadedTools  []StoredToolSpec  `json:"loaded_tools,omitempty"`
}

type StoredToolOutput struct {
    Type       string          `json:"type"` // function_call_output/custom_tool_call_output/tool_search_output
    CallID     string          `json:"call_id"`
    Name       string          `json:"name,omitempty"`
    Output     string          `json:"output,omitempty"`
    Status     string          `json:"status,omitempty"`
    Execution  string          `json:"execution,omitempty"`
    Tools      json.RawMessage `json:"tools,omitempty"`
}

type ResponseRecord struct {
    Version              int
    ...
    InstalledToolCatalog *StoredToolCatalog    `json:"installed_tool_catalog,omitempty"`
    LoadedToolEvents     []StoredLoadedToolEvent `json:"loaded_tool_events,omitempty"`
    ToolOutputs          []StoredToolOutput     `json:"tool_outputs,omitempty"`
}

The names can change. The durable schema needs explicit JSON fields and a version number. Store the canonical Responses identities and the semantic keys of the catalog. Make the SDK aliases again when you configure a session. Keep the continuation inputs of the client and the tool outputs separate from the response.output items that the API shows.

HTTP flows and WebSocket flows

Flow Necessary behavior
Initial HTTP response Normalize the tools of the request. Store the installed catalog and the semantic key. Give tool_search and each tool that is not deferred to the model.
Live HTTP continuation with a search output The planner checks the active outputs, finds the effective catalog and merges the loaded tools. It stores the transcript of the tool output and the catalog. It stops the old runner. It starts one SDK turn with the merged catalog, synthetic or resumed with proof. It returns the next model response.
Streaming continuation Use the same planner decision as the non-streaming path. Send the lifecycle events of the turn after the search only. Keep a stable response id, stable sequence numbers, stable output indexes and a stable owner of the pending batch.
WebSocket continuation Send response.create through the same planner at the level of the gateway. Keep the sequence numbers, the rule of one active response and the behavior of the top-level errors.
Warm session with generate:false Either support the tool-output continuations through the same merge planner and prepare the turn after the search, or give a clear error until the proxy supports it. The reuse of a warm session compares the semantic keys of the catalog.
Cold fallback, restart or TTL Find the catalog in the previous response record. Build a transcript again with the previous assistant calls, the tool outputs of the client, the search results, the availability of the loaded tools and the last user text. Do this before you configure the synthetic turn.

Table of the checks

Input Behavior
tool_search_output.tools contains loadable functions Accept them. Merge them into the catalog. Give them to the model in the next turn, if the ownership, the status and the execution of the pending call are correct.
tool_search_output.tools contains a namespace with function children Accept it. Make the children flat. Keep the namespace on the output calls.
A returned tool repeats a definition that is installed and identical Accept it. It makes no change. The history data can record the repeated search event outside the semantic key.
A returned tool has the same identity or the same SDK alias as an installed tool, but a different definition Reject the continuation before you complete or cancel the pending batch.
More than one tool_search_output item in one live parallel batch Check all the active outputs. Then merge the loaded sets in the order of the call_id values. Reject the full continuation if there is a conflict.
An empty tool_search_output.tools Record the search output. Do not change the catalog.
tool_search_output.status is failed, incomplete, cancelled or unknown Record the output text. Do not install the tools. Reject the request if a failed status contains tools, except when you process them as metadata that installs nothing.
A returned tool that is hosted or that the proxy runs, or a field of a hosted provider Reject the returned specification. Do not install it without a message.
A returned custom tool or a nested tool_search Reject it in this iteration.
A returned nested namespace Reject it.
The continuation has tool_choice: "none" Keep the merged catalog state. Give no callable tool to the model in that turn. Use the sentinel only.
The SDK sends a request for a tool that is not configured Stop the turn with an error. This is a protocol error of the upstream system. Do not return it as a call that the client can see.

Test plan

Unit tests

  • The merge of the catalog with functions and with namespaces. This includes a duplicate load that makes no change.
  • The rejection of a collision with the current tools, with the loaded tools, with the aliases and with the sentinel.
  • The canonical catalog keys ignore the order of the raw JSON, but they keep the fields that have a meaning. The history data is not part of the semantic comparison.
  • The proxy rejects a returned specification that is hosted, custom, a tool_search or a nested namespace.
  • The allowlist of the fields rejects a field of a hosted provider or an authentication field or a server field inside a function specification or a namespace specification.
  • The status control: a completed status installs the tools; a failed status or an incomplete status does not install them.
  • The permission handler approves only the merged SDK aliases of the current request. With tool_choice:none the model gets the sentinel only.

Gateway tests

  • A live tool_search_output with a loaded namespace starts one turn after the search, with the merged AvailableTools.
  • The proxy cancels the old runner and discards its results. It removes the broker batch. It sends no result that comes from the old catalog.
  • The next tool request of the model for multi_agent_v1.spawn_agent becomes a function_call with a namespace.
  • An incorrect output kind, name, status or execution, and an incorrect previous response id, cause an error before a change of the state.
  • The cold fallback builds the search output, the availability of the loaded tools and the effective catalog again from the stored record.

Tests for the streaming, the WebSocket and the warm sessions

  • The streaming continuation sends the lifecycle events of the turn after the search only. The response id, the sequence numbers and the output indexes are stable.
  • The WebSocket response.create supports the merge of the search output and the calls to the loaded tools, through the same planner.
  • The behavior of a warm session with generate:false is either supported through the merge planner or rejected with a clear error.
  • The tests for the reuse of a warm session and for a session that does not agree include the merged catalogs and the semantic catalog keys.

Repeatable tests for the function and for the safety

  • The fake SDK and the fake provider record the exact merged SDK tool names and the filters. They send a call to a loaded tool only when that tool is present.
  • The aliases do not occur in the SSE events, in the WebSocket events, in ResponseRecord.Output, in the fallback transcripts or in the usual log summaries.
  • No SDK built-in tool, no sub-agent process, no shell tool, no MCP tool, no file tool and no host git operation becomes available after a dynamic installation.
  • Manual test with the Codex CLI: find multi_agent_v1, call a sub-agent operation that makes no change, wait, and close.

Risks and corrective actions

Risk Corrective action
The old SDK turn continues with the old catalog Use the synthetic replacement by default. Check, merge and store. Then stop the old runner and discard its results. Then remove the batch, and start one turn with the merged catalog.
The resume operation of the SDK does not replace the tools Do not depend on the replacement during a resume until a live integration test shows it. Use the synthetic continuation by default. Add the resume optimization behind a separate control.
The catalog state is lost after a restart Store the installed catalog with a version, the events of the loaded tools, and the structured tool outputs on the response records.
The loaded tools become tools that the proxy runs Keep the handlers parked. Keep the permissions limited. Keep the SDK built-in tools disabled. Keep the allowlists for the returned specifications strict.
A dynamic catalog shows sensitive schemas or descriptions Store the canonical specifications with the minimum data. Set limits on the sizes. Truncate the logs. Write in the documentation how long the proxy keeps the data locally, and how a purge operates.
The catalog state becomes different between the HTTP path, the WebSocket path and the warm sessions Use one shared planner and one shared catalog module for all the transports.
The aliases change the planning of the model, or they go to the client Keep the canonical names in the descriptions, and return the canonical names to the client. Add tests that show that the aliases are not in the API outputs or in the usual logs.

Acceptance criteria

  1. A live tool_search_output that contains a multi_agent_v1 namespace causes the next SDK turn to contain synthetic custom tools for the child functions.
  2. The proxy cancels the old runner with the old catalog and discards its results. That runner cannot send a second final response or an old final response.
  3. The model can call a loaded tool, for example multi_agent_v1.spawn_agent, after the boundary.
  4. The proxy sends a function_call with namespace: "multi_agent_v1" and name: "spawn_agent". It does not send the SDK alias.
  5. The Codex CLI runs the loaded tool and continues with a function_call_output. The proxy never runs the tool.
  6. The proxy stores the returned loadable tools in the canonical catalog state. The state stays available for the later continuations and for the fallback after a restart.
  7. The non-streaming HTTP path, the streaming HTTP path, the WebSocket path and the warm-session path use the same merge planner for the catalog. If a path does not use it, that path gives a clear error behind a temporary control that the documentation describes.
  8. The proxy rejects these items: a returned tool that is hosted or that the proxy runs, a field of a hosted provider, a nested namespace, a returned custom tool and a returned nested tool-search tool.
  9. A tool_search_output.status that is failed or incomplete installs no tool.
  10. A request with tool_choice: "none" and an installed dynamic catalog gives no callable tool to the model in that turn.
  11. No built-in Copilot SDK tool, no MCP server in the proxy, no shell tool, no file tool, no repository tool, no host git operation and no sub-agent process becomes available after the dynamic tool installation.
  12. The tests show that the tools are not callable before the boundary, and that they are callable after the installation of the merged catalog.
  13. The README does not contain the old limitation. That limitation says that the returned tool_search_output.tools need a later request with an installed catalog.
